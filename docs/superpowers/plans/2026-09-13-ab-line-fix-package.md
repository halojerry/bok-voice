## 乙、垫话拟人化 v4:垫话罐头体系(语境确定性命中,拒绝随机抽签)

**设计前提**:垫话的目的是垫住 LLM→TTS 静默窗(覆盖机制不动),但用户拍板:**随机触发本身就没有真人感**——同一客户说同样的话,这次「嗯,好」下次「唔好急等一陣」,话术漂移=机器感。真人客服恰恰是高度套路化的:同样的场景说同样的话,**确定性不是机器感,随机才是**。所以垫话升级成 QA 罐头同款体系:语境→条目确定性命中,随机只存在于回退层。

### B1 垫话罐头体系(filler_entries 表,镜像 qa_entries 全套已验证基建)

复用 QA 罐头已跑通的全链路(HybridLexical 匹配/tts-pregen 物化+pin/web 运营表单/tts-mine 挖掘),新增 `filler_entries` 表(字段对齐 qa_entries:id/lang/category/trigger_pattern/text/voice_id/audio_path/priority/per_call_cap/enabled/source/created_at):

1. **命中选取(确定性主路径)**:垫话 arm 时,用**客户上一句**过双通道匹配——HybridLexical(0.6×余弦+0.4×子串,复用 qa_gate 既有组件,trigger 样本即条目示例句)+ category 正则——取最高分条目,同分取 priority 高者;同一条目每通命中计数封顶(per_call_cap,防同语境连击)。全程打点 `BOK_FILLER_MATCH entry=... score=...`,miss 才走回退。DB 里没有的池子也要有兜底,但主路径永远先问罐头库。
2. **回退梯**:命中条目 → 分类器池(五类正则,B2)→ 通用池。分类器是兜底,不是主路径。
3. **初始种子条目**(一期入库即用,三语 ~20 条):从 285 条实机配对取最高频 6 场景,每场景 2-3 条变体(变体是给**不同通**用的防腻,不是同通随机)——「问赔几多」「查单进度」「报号码/报平台」「想投诉/抱怨」「纯短应承」「默认承接」。trigger 与文案见 B5。
4. **已知回复路径零随机(先行批)**:say_step 直念步与 QA 快路的回复在垫话 arm 时**已知**——这两条路径不走匹配,直接由回复内容确定性映射(赔偿档直念前→「嗯……点样赔,等我讲你知」;QA 命中→「等我睇返先」)。这是第一批"绝对不穿帮"条目。
5. **挖掘闭环(运营自学习,复用 tts-mine)**:真实通话 turns 挖高频客户话式 → 建议 trigger+text → web 运营页审核增删(镜像 reports/qa-pairs --apply 流程)→ `tts-pregen --fillers` 按人设音色物化+pin。客户用得越多罐头越贴,与 QA 罐头同一飞轮。
6. **kill-switch**:`BOK_FILLER_MATCH=0` 整个体系回退纯分类器(现行为),`BOK_FILLER=0` 全关——两级开关与现有惯例一致。

### B2 分类器(回退层):四类+默认,只看客户上一句(`fillers.py` 纯函数)

| 类 | 判据(优先级从高到低) | 垫话该做什么 |
|---|---|---|
| **B 安抚** | 投诉\|嬲\|烂咗\|未到\|太耐\|太长\|激气\|慢\|急\|生气\|着急 | 接住情绪,**零动作动词** |
| **A 确认接收** | ≥4位数字串\|WhatsApp\|微信\|單號\|淘宝\|拼多多\|京東\|eBay\|Amazon | 确认「听到了」,别催别查 |
| **C 查证** | 查下\|查询\|边度\|幾時\|幾多\|点解\|点样\|进度\|到未 | 思考/查询口吻——**动作词只准此类用** |
| **D 短应承** | 全句 ≤4 字或纯 嗯\|啊\|好\|系\|哦\|得 | 极短应承 |
| **E 默认** | 分不出 | 通用 |

铁律:A/B/D/E 四类池零动作动词(治「问赔多少→马上查」式穿帮,285 条配对实证该模式占开火 ~60%);优先级 B > A > C > D > E。

### B4 时长双档保覆盖(机制不动)
