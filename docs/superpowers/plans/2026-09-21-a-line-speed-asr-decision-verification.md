## 0. 这份计划是什么、不是什么

**是**：一组**不改仓库源码、不改任何默认配置、不重启在跑的任何服务**的测量。把候选方案（LAY A、LLM2Jev 式
typed decision、热词扩容、输出端校正、Qwen 4B 参数档位）从「机制上讲得通」推到「本机跑出来是多少」。

**不是**：实现。本文里所有「可能的修法」都只是**待验证假设**，验证通过才进后续的修复计划。

## 2. 决定计划形状的五个前期发现

### D1 ⭐ mlx-lm 原生支持「只 prefill 不生成」的判类型决策——这条最值钱

两件事凑在一起：

1. mlx_lm server 的请求体支持 **`logprobs`（1-10）** 与 `max_tokens`；
2. 参考项目 **LLM2Jev**（Yinsongxu/LLM2Jev，apache-2.0）的核心方法正是 **"prefill-only binary inference"**
   ——不要求模型「生成一个标签再解析」，而是问一个是非题、**只读下一个 token 的概率**，从不真的自回归解码。
   该项目同样接受运行时定义的 **Choice / Score / Noul** 三类问题，与 LAY A 是同一个接口形状，
   区别是它**不训新模型**，用本地现成的 HF 模型跑（经 `--model-path` 指定）。

**合起来的意义**：我们**可以在现有 mlx_lm server 上用现有 4B/9B，做同款 typed decision，零新依赖、
零新运行时、零仓库改动**（一个 curl 就能验）。可行性论证见 §3 V-1。

**为什么这条比 LAY A 更重要**：它直击 `docs/A_LINE_LOGIC.md` §10.4 那个「迟一轮」的结构洞。
当前 L4/L5 之所以需要 pending 槽 / TTL 一轮 / store 守卫 / 单飞 / fire-and-forget / 下一轮消费，
**唯一原因是 judge 是 9B 生成模型、慢到只能异步**。判定从「生成自由文本再正则解析」改成「读一个概率」，
这套异步脚手架就不再必要——不是优化，是**可以整块删掉**。

### D2 LAY A 在我们机器上**没有 MLX 路径**

- mlx-lm 的 `mlx_lm/models/` 架构目录里**没有 ModernBERT / mmBERT** → 无法用 MLX 跑；
- LAY A 官方只提供 `pip install laya`（PyTorch + transformers），模型卡与 PyPI 页**均未提 MPS / Apple Silicon**；
- 模型卡自己的 CPU 数字：预载后 **193–464 ms/问**，CPU 重载 **7.4 s**，懒路由语言切换 **7–10 s**；
- 那个诱人的 **32.8 ms 是 T4 的数字**——我们没有 T4。

**判定**：LAY A 的 33ms 对我们不成立。CPU 档 193–464ms **高于**「同轮同步」预算（判据表见 §3 V-1），
MPS 能否进 300ms 未知，且 PyTorch 在一个纯 MLX 本地栈里是**第二套运行时**。
→ **LAY A 降为 V-1 的 Track B（对照组），不是主路。**

### D3 LAY A 的**接口**是对的，而我们可以用自己的模型实现它

LAY A 的 `criteria` 是 `{标签: 描述}`、**推理时逐次传**——这个接口设计是对的，也正是「意图词预填充」的
天然容器（运营写一次，模型当选项集用，无需训练）。

既然 D1 已证明我们能用 MLX 做同样形状的 `choice / noul / score`，那么
**「LAY A 的接口」与「LAY A 的模型」是可以分开取的**：取接口（typed decision + 运营给的 criteria），
模型用我们自己的、已经热的、原生 MLX 的 4B。这是 V-1 Track A 的理论基础。

### D4 `--kv-bits` 会杀掉 batching（禁用项，不是候选）

mlx-lm `SERVER.md` 原文：量化 KV cache **不支持 batching**，该模式下服务**串行处理请求**。
我们是 4–6 路并发会话——开 `--kv-bits` 等于杀掉并发。**列为禁用项**。

### D5 ASR 侧：模型对粤语不差，缺的是**输出端校正层**

Qwen3-ASR 官方卡数字：**粤语 Fleurs-yue 3.98 / WenetSpeech-Yue 5.82 \| 8.85** / CV-yue 7.57；
官话 WenetSpeech 4.97 / AISHELL-2 2.71；52 语言方言，明确列出 **Cantonese (Hong Kong accent) /
Cantonese (Guangdong accent)**。模型侧并不弱。

而我们的实弹问题（九→狗、號→后 同音滑失，京|東 品牌词拆分）是**特定词在特定上下文里输了**。
到目前为止我们用过的全部手段都在**输入端**：热词 context 偏置（≤200 字符）、8bit 维持、
跨段 join-hold、句级/子句/长度提交。**输出端从来没有过校正层**——
把已知词表 + 数字语法 + 对象词（courier / tracking_tail / contact_channel）+ 模板变量拿来做**一次受约束的
后校正**，这个杠杆**从未试过**。→ V-3 的新线。

## 3. 五条验证线

### V-1 决策层选型（最高优先：决定 §10.4 结构洞能不能消掉）

**问题**：能否在 <300ms 内、用我们自己的模型，对一轮转写给出「意图归属 / 是非判断 / 强度分」？

#### Track A —— MLX prefill-only typed decision（主路）

| 步 | 动作 | 会暴露的第一个问题 |
|---|---|---|
| A1 | 对 :1235 发 `POST /v1/chat/completions`，`max_tokens: 1`，`logprobs: 1-10`，prompt 构造为「……只回答 是 或 否」 | **响应形状**：mlx_lm server 回的是 `logprobs` 还是需要 `top_logprobs`、回几个候选、中文单字是否独立成 token。若拿不到 top-k，就得改问法（如让模型输出单个数字 token） |
| A2 | 读 `是` / `否` 两个 token 的 logprob → P(是) | 4bit 权重下**概率分布是否还有判别力**（见下「最大风险」） |
| A3 | 用真库副本的 N=30 条真实转写（**含 L-① 漏网轮**），构造三类问题各跑一遍：`choice`（本步归属，选项 = 该步 scope 内图意图标签）、`noul`（是否拒绝 / 是否报号 / 是否应承）、`score`（情绪强度 3 档） | — |
| A4 | 记：单问端到端墙钟（含 prefill）、P 值分布直方图、与现有 L1/L3 输出的**一致/不一致清单** | — |

**最大风险**：我们的 4B 是 **4bit** 量化，而量化会**劣化概率分布**——若 P 值糊成一团没有判别力，
Track A 就需要先解决量化档位（48GB 内存无压力，可试 8bit 4B，代价是显存与速度），或退回生成式。
**这是本计划里最需要尽早知道答案的一件事，A1-A2 半小时内能出结果。**

#### Track B —— LAY A 对照（可选项）

| 步 | 动作 |
|---|---|
| B1 | **独立 scratch venv**（不污染 `.venv312`）：`pip install laya`；记实际拉进来的 torch 版本与体积 |
| B2 | device 探测：MPS 可用否、加载 mmBERT-base 要多久、单问延迟。**若 >1s 直接判死，不必往下跑** |
| B3 | 同一批 30 条转写 + 同一批 criteria（用运营真词表），跑 `laya-multilingual` |
| B4 | 与 Track A 逐条对照 |

**注意**：zh / cantonese 必须走 `laya-multilingual`——模型卡自陈英文 checkpoint 在非拉丁文字上
「stays confident while being wrong」（高棉语 0.000 准确率 @ 0.952 置信），
而 **confidently wrong 恰恰是收线场景最危险的失败模式**。

#### 判据表（同步可用性）

| 单问延迟 | 判定 |
|---|---|
| **< 300 ms** | 可同轮同步 → **L4/L5 的 pending / TTL / store 守卫整套可删** |
| 300 ms – 1 s | 需与别的东西重叠，架构收益减半 |
| > 1 s | 只能继续异步 → 无架构收益，退为「提升召回」用途 |

300ms 这个门槛的依据：当前垫音链发能覆盖的等待窗是 ~1.5–2.3s，判定若落在 300ms 内
则**不需要任何垫音**就能同轮完成，体感上等于「零等待」。

### V-2 LLM 提速（活通话主路径）

**问题**：现有 4B 的 TTFT 还能不能压。

| 步 | 动作 | 约束 |
|---|---|---|
| 2.1 | **`--prefill-step-size` 重 A/B**：现设 512，依据是 2026-09-08 那次二分（512 优于 1024，官方默认 2048）。**但那次是哪台机器上做的？** 若在 16GB 机上，结论不保证迁移到 48GB | **在空闲端口（如 :1239）起第二个 mlx_lm server** 加载同一颗 4B，`--prefill-step-size 2048`，同一批 prompt 对打。**绝不重启 :1235** |
| 2.2 | **`iogpu.wired_limit_mb`**（macOS 15+，`sudo sysctl`）。mlx-lm 文档提到大模型下有收益 | ⚠️ **动的是系统级参数、影响同机所有会话（含别人在跑的栈）→ 需显式批准才做**；必须留改动前读数、事后可回滚 |
| 2.3 | **并发退化**：4–6 路时 TTFT 劣化多少 | 用 `scripts/load_audio_concurrency.py` 的口径但**降到 2 路并缩短**，避免压到真实会话。基线从 `llm.log` 的 `LLM_TTFT_MS ... cached=N/M` 取样 |
| 2.4 | **明确不测**：`--kv-bits`（D4：杀 batching）；`draft_model` 投机解码（AGENTS.md 记录会关 continuous batching —— 列为**待复核**，因为若它其实不关，4B 上投机收益可能不小） | — |
| 2.5 | **量化档位**：现 4bit。若 V-1 需要更干净的 logprob，同端口 A/B 8bit 4B | 内存无压力，代价是显存与速度 |

### V-3 ASR 提准

**问题**：剩下那些同音字滑失 / 品牌词拆分，能不能在**输出端**救回来。

| 步 | 动作 | 备注 |
|---|---|---|
| 3.1 | **热词边际复核**：复用 `scripts/probe_hotword_ab.py`（三档 none/current/extended × 10 碎裂句） | 2026-09-17 那次的结论要在这台机器上重跑一遍（模型/硬件可能都变了）。注意当年已发现**探针有 ±2-3 句渲染方差**，必须跨渲染采样 |
| 3.2 | ⭐ **输出端受约束校正（新杠杆，从未试过）**：离线拿历史转写，用「热词表 + 数字语法 + 对象词（courier / tracking_tail / contact_channel）+ 模板变量」做后校正，看能修回多少 | 零代码做法：真库副本导出转写 → 纯文本规则在 `/tmp` 脚本里跑（经 Write 工具，**不进仓库**）→ 对 E2E 固定句集量 CER 前后。**这是「加一层」不是「改一层」**，不碰 `_echo_filter` / join-hold |
| 3.3 | **数字专线**：号码捕获现在是 4 位起收 + `_digit_normalize`。离线统计真实报号轮里 ASR 究竟错在哪几个数字上 | 这是「零降级铁律」的核心区，值得单独一张表 |
| 3.4 | **云杯对照（可选，需 key）**：Qwen3-ASR 卡提到 DashScope 有实时 / FileTrans API。同一批真实音频离线跑一遍比 CER | **判断点**：提升 <2 个点 → 不值得引入网络依赖；>5 个点 → 值得讨论混合路由。<br>⚠️ 这条是唯一的**外部**请求路径，若要走，服务端侧必须先有 host 校验（拒绝回环/私有/保留地址） |

### V-4 意图词预填充可行性

**问题**：把现有词表当 `criteria` 喂进去，零样本命中率够不够。

| 步 | 动作 |
|---|---|
| 4.1 | 从真库副本构造「每步的意图词集合」：步骤 `goal` + `ref` 首行 + 分支 `cond` + 图意图 `keywords` + **`qa_entries.question_text`（按 `scope`/`step_index` 归属到步）**。**这一步本身就会暴露覆盖率问题**（哪些步一个词都没有） |
| 4.2 | 用 V-1 Track A 的 logprob 决策，对 L-① 漏网轮跑 `choice`，看能否把「关键词没中」的轮次判对 |
| 4.3 | ⭐ 这张表**同时就是 O 类问题的登记表**：哪一步没词、哪条 QA 从没被当成意图语料、哪些词互相冲突 |

**为什么 4.1 值钱**：`source=mined` 的那些 QA 问法是**从真实通话里挖出来的客户原话**，
今天**只**用于 0.90 字面匹配，**从未被当成「该意图的示例说法」提供给意图层**。
它们恰恰是最好的示例说法。这一刀切下去，话术意图与 QA 就共享了同一个词表——
不需要把两个系统合并（那会毁掉 QA 作为独立召回通道的正交性），只要让 QA 的问法**同时**充当意图语料。
这是 `docs/A_LINE_LOGIC.md` §10.9「共享词表、各留判据」的具体第一刀。

## 5. 产出与执行顺序

**本轮结束时的交付**：

1. V-1 … V-5 各线读数与判定（含 Track A/B 对照表）
2. **问题登记册**（预计 15–30 条）
3. **决策层选型建议**（Track A / Track B / 维持现状），带数字
4. 由 1–3 导出的**修复计划**（分优先级，每条带预期收益与风险）

**顺序建议**：

```
V-1（先行：它决定要不要动 L4/L5 架构，也决定 V-4 用什么工具）
 ├─ V-3（并行：ASR 独立、且是准确度的大头）
 ├─ V-2（插空：需起第二实例，别和 V-1 抢机器）
 └─ V-4（依赖 V-1 的 Track A 结论）
V-5 收尾全跑
```

**写在前头的风险**（避免中途才发现）：

- **4bit logprob 不可用**会让 Track A 必须先解决量化档位问题——所以 A1/A2 要最先做；
- **第二实例 + LAY A + 探针同时跑会在 48GB 上抢 GPU**，读数互相污染 → **串行执行，单次只跑一条线**；
- 真库副本导出前先确认对象/号码都是测试数据。
- V-2.2（`iogpu.wired_limit_mb`）是唯一需要**显式批准**的系统级动作。

### 6.1 延迟与准确率（决定性数字，4B vs 9B 同一把尺子）

统一仪器：`/tmp/v1g_prod_cache_ab.py` —— 同一份「按步静态 system（12 候选表）」，7 句真实口吻转写，
ground truth 人工标注，**缓存开 / 破缓存两档对照**。

| 形状 | 4B :1235 | 9B :1237 | 判据 300ms |
|---|---|---|---|
| **生产形状 · 缓存吃满** | **6/7 · 平均 176ms** | **7/7 · 平均 413ms** | 4B ✅ / 9B ✗ |
| 破缓存（前缀不复用） | 6/7 · 180ms | 7/7 · 1006ms | — |
| 短 prompt 暖（~65 tok，`v1b`） | median 158ms | median 408ms | — |

**三条结论**：

1. **前缀缓存的收益是 2.4–4×，且不损失准确率**（同题同分，只是变快）——
   由 A/B/C 三变体隔离确认（见 6.3），不是猜的。
2. **4B 在生产形状下 176ms，稳在 300ms 判据内**；9B 413ms，**超出**。
3. **准确率上 9B 略优（7/7 vs 6/7），但只差一例、样本 n=7，不足以定论。**
   那唯一一例是英文句「Hello, is this about my parcel?」——9B 正确判 `查詢進度`，4B 判成 `問平台資料`。
   **准确率结论必须等 V-4 用真实挖掘语料放大样本后再下。**

**⭐ 但这里有个战略要点，比"选哪个模型"更重要**：**收益来源不是"用 4B"，而是"把生成式判定换成 prefill-only 判类型判定"。**
9B 即使 413ms，对比现状（生成式 judge，`timeout=20s`、迟一轮、需要 pending 槽/TTL/store 守卫）
仍然是**几十倍的提速 + 同轮同步**。所以：
**4B 用来做「必须 <300ms 的同步判定」；9B 用来做「可以多花 400ms 但要求更准的判定」——两者按判定用途分工，不必二选一。**

`noul` 两个原始「miss」经复核是**我的标注错了**，不是模型错：「你係邊個？」答 否、

### 6.3 三次更正后的最终定性：位置扫描的异常是**窄条件触发**，不污染生产形状

| 实验 | 形状特征 | 4B | 9B |
|---|---|---|---|
| 位置扫描（`v1e`） | **12 次请求 user 轮完全相同，选项表只挪动一项** | **2/12**（10 次答 B） | 12/12 |
| 缓存 A/B（`v1f`） | 同上，加唯一 nonce 破缓存 | **10/12** | — |
| **生产形状 A/B/C（`v1g`）** | 静态 system + **每句不同的 user 轮** | **三个变体全 6/7**，连失败的都是同一例 | 7/7 |

**定性**：`v1e` 那个 2/12 是**真实存在但触发条件很窄**的现象 —— 需要
「user 轮逐字相同 + 选项表只做单点位移」这种**非自然输入**。
一旦回到生产形状（客户那句话每次都不同），**三个变体给出完全相同的答案与相同的唯一失败例**，
说明**前缀缓存不污染判定**。`v1f` 里 nonce 一加就从 2/12 变 10/12，但 `v1g` 证明那不是"缓存坏了"，
而是**破缓存同时改变了模型对近同文上下文的注意力**——两者纠缠，**机制仍未查清，已登记为 V1-11**。

**⭐ 顺带测出并写进实现约束的**：候选表放「按步静态」system 前缀 → **176ms**；
放 user 轮里逐请求变化 →（`v1d`）**348ms**。**候选清单必须进静态前缀。**

### 6.4 仍然成立的阻断性发现

1. **logprob 不是归一化分布**（V1-03）：`Σtop10 = 1.001 … 1.052 > 1`，10/14 样本越界。
   数学上不可能是 softmax。→ **`exp(logprob)` 不能当概率用**：排序可信、**绝对置信度不可信**。
   直接后果：**`noul` 不能作为合规闸的置信度依据**（「P(收线)=0.88」并不意味着 88% 该收线）。
   阈值只能**逐问题在真数据上经验拟合**。
2. **token 字符串乱码、只能按 `id` 比对**（V1-02）：同一响应里 `message.content` 是正确的「是」，
   而 `logprobs.*.token` 是 `æĺ¯`（码点 0xE6/0x13A/0xAF）。
   → 实现必须**按 token id 建映射**。（首轮探针 17/17 假 miss 的根因。）
3. **阿拉伯数字 ≥10 不是单 token**（V1-10）：`max_tokens=1` 下 "10" 读到的是 "1"，
   标定 12 个数字只成功 9 个。→ **标记必须用保证单 token 的符号**（ASCII 字母 A–L 实测 12/12）。
4. **服务端入参不校验、直接断连**（V1-01）：`top_logprobs > 10` 时不返 400。

筛 `line=="a"` 且 `role=="user"` 的真实客户转写，去重取长度 2–60 的 30 条。**全程只读，不写库。**

| 模型 | 墙钟 | 一致率 |
|---|---|---|
| 4B :1235 | median **242ms** / p90 251 | **6/30 = 20%** |
| 9B :1237 | median **318ms** / p90 330 | （同上） |

**一致率只有 20% —— 两个模型在 30 条真实转写上有 24 条判得不一样。** 但看分歧样本，
结论不是"选型很重要"，而是**被判定的东西本身已经坏了**：

| 真实转写（原文照录） | 问题类型 |
|---|---|
| 「好。我想了解一下**女**。」「你好。我想了解一下**女**。」 | **同音字滑失**（你→女） |
| 「想查下我账单，**去天热道尔道个**。」「查下我张丹**去天热道玩道个**。」 | 整段退化，非语言 |
| 「你帮我睇**。**一下。」「你帮我睇**。**底下。」「快，你帮我睇。」 | **碎裂提交**（句号=微停顿切轮） |
| 「查下我。**我张单，麻生**你帮我推下。」 | 碎裂 + 同音（麻煩→麻生） |
| 「Hello. I would like to know more about **your**.」 | 外文截断 |
| 「旗下。」「地下。」「底下。」 | 纯碎片 |

**两个模型的失败方式不同，且都反映输入已坏**：
- **4B 塌向单一标签 `F`（問平台資料）** —— 对受损文本给出一个**恒定答案**，是危险的失效模式
- **9B 分散到 `L`（其他）/`A`（查詢進度）/`D`/`B`** —— 大量落到「其他」，对垃圾输入反而是更诚实的答案

**这条发现把优先级改了**（原先 V-1 排第一）：

1. **决策层不是瓶颈，ASR 转写质量才是。** 我们在拿一块坏掉的文本去问"它属于哪个意图"——
   无论换 LAY A、换 4B、换 9B，都是在坏输入上做分类。
2. **`V-3`（ASR 提准）应当升到 `V-1` 之前**，尤其是 `V-3.2`（输出端受约束校正）
   与 `V-3.3`（数字/同音专线）——它们直接改善的是**判定层的输入**。
3. **决策层选型不得在受损语料上定**：`§6.1` 的 6/7 vs 7/7 是干净语料上的数；
   真实语料上 20% 一致率说明**两模型都不可信**。选型结论必须等 ASR 改善后重测。
4. **4B 的"塌向单标签"是独立风险**：即使输入干净时它表现好，一旦输入退化它会给出**恒定答案**，
   而恒定答案在客服场景意味着**系统性答错**。这条给 `§6.1` 的"4B 更实用"打了一个折扣，
   也说明**必须有置信度/一致性护栏**——但见 `V1-03`：logprob 未归一化，护栏不能直接用它。

### 9.1 V-3.1 热词边际归零

**`extended` 相对 `current` 逐句零增益**（唯一增益句 7 来自 `current`）。

**⚠️ 方法论修正（第 4 次差点被测量骗，这回先拦住了）**：本探针**每句只合成一次音频、三档两轮共用同一条**，

### 9.2 V-3.2 输出端音学校正：上界只有 4–5/10，且有 8 路歧义

用 pypinyin + ToJyutping（装在**独立 scratch venv** `/tmp/v32venv`，不碰项目 `.venv312`），
对每个关键词在转写里做**等长**音近定位（音节级编辑距离，普通话/粤拼两侧取优、去声调）：

| 定位结果 | 句数 | 说明 |
|---|---|---|
| 距离 0 原样在 | 3 句 | 機器人 / 好講 / 邊度 —— **本来就对，校正零收益** |
| 距离 1 唯一候选 | 5 句 | 單號←单后、幾多←劲多、賠到←皮到、詐騙←再骗、證明←整改 |
| **1 字关键词 8 路歧义** | 2 句 | 嬲、倉 —— 对**任意单字**都是距离 1，无法判别 |
| 不可定位 | 若干 | 呃人 / 賠償 / 多少 / 號碼 —— 正确的音在转写里**不存在** |

→ **输出端校正的真实召回上界 ≈ 4–5/10**（3 句已对 + 2–3 句可信候选），
且必须「只打多字关键词 + 只接受唯一候选」才能压住假阳性（`再骗`/`整改`/`劲多` 都可能是真实短语）。

**⚠️ 第 5 次测量错误（已修正）**：本测试第一版允许滑窗长度 ±1，导致
「2 字关键词 vs 任何单字」= 删除距离 1、「1 字关键词 vs 任何字」= 替换距离 1，
汇总**假出「10/10 可救」**。改成等长后才得到 4–5/10 的真实上界。
**教训：编辑距离类指标必须禁止长度不等，否则会退化成「文本里有没有字」这种恒真判据。**

### 9.3 ⭐ V-3 关键对照：语义不能吸收 ASR 损伤（猜想被证伪）

`/tmp/v3b_semantic_vs_repair.py` —— 同一批 10 句，同一份 12 选项表，两臂对照：

| 模型 | clean（源句） | **asr（损坏转写）** | 衰减 |
|---|---|---|---|
| 4B :1235 | **9/10** · 268ms | **4/10** · 238ms | **−5** |
| 9B :1237 | **10/10** · 371ms | **6/10** · 314ms | **−4** |

**两个结论，一个正面一个致命**：

1. **正面：typed decision 架构在干净文本上成立得很好** —— 9B 10/10、4B 9/10。
   这是对 §6.1「架构成立」的独立确认，且这次用的是**语义标注的意图选项**（不是关键词命中）。
2. **致命：我上一轮那个猜想被证伪。** 我在 §7.5 写过「语义模型可能比子串匹配更抗 ASR 损伤」——
   数据说**不成立**：损坏转写上 4B 掉到 4/10、9B 掉到 6/10。**损伤不是表层错字，是内容被销毁。**

看句 2 就清楚为什么：「點證明你唔係呃人嘅」→「点进营，你有细节整改。」
——**这已经不是拼写错误，是语义消失**，人类也无法从转写还原意图。
而句 7（去→写，仅表层错字）两模型都判对。

**所以是两种regime**：
- **表层损伤**（去→写、倉→钱、單號→单后）→ 可恢复，模型也吃得住
- **内容销毁**（点进营/你有细节整改、你咪再骗几条呢个）→ **任何后处理都无解**

这解释了 §9.1 的「热词扩容零增益」：**词表偏置治不了内容销毁。**

### 10.2 ⭐ V-4 小模型表达校正：不成立（用户假设的直接检验）

**用户假设**：「用户输入的时候小模型做表达校正」——参考 Type4Me / akang-ai-voice-input / VoxType
三个语音输入法的形态（`录音 → ASR → 小模型清理 → 上屏`）。

**先修正上一轮实验的一个漏洞**：V-3b **没给步骤上下文**，而上下文恰是「内容销毁型」句子唯一可能的救赎。
本轮补上步骤上下文（第 3 步 / 索取号码 / 客户常见反应），四条件对照：

| 条件 | 4B | 9B |
|---|---|---|
| clean+ctx（天花板） | 9/10 | 9/10 |
| local+ctx（现状） | **5/10** | **6/10** |
| cloud+ctx（换 ASR 端到端） | 5/10 | 6/10 |
| **rewrite+ctx（小模型校正后判定）** | **5/10** | **6/10** |

**`rewrite` 与 `local` 逐句完全一致，连失败的句子都相同。校正层净价值 = 0。**

**为什么？看校正层实际产出就懂了**：

| 原转写 | 小模型「还原」后 |
|---|---|
| 你咪再骗几条呢个？ | 你咪再**騙**幾**條**呢**個**？ |
| 点进营，你有细节整改。 | 點進營，你有**得**細**緻**整改。 |
| 我已经当做好耐啦。 | 我已經當做好耐啦。 |
| 你哋个钱喺边度噶？ | 你哋個錢喺邊度噶？ |

**它一个字都没改对——只做了繁简转换。** 唯一的变化是 4B 在句 2 插了个「得」字。
原因很直接：**模型无从知道客户实际说了什么**。文本里没有这个信息时，
让它「还原客户本意」只可能有两种结果——**照抄原文（本轮的实际行为，安全但无用）**
或**编造（危险）**。它选择了照抄，这是对的，但也说明这条路没有信息可提取。

**为什么语音输入法那套不适用**（三个参考项目都读了）：

| | 语音输入法（Type4Me / VoxType / akang） | 我们（A 线外呼） |
|---|---|---|
| 说话人意图 | **就是要产出文字**，配合、吐字清楚 | 接听陌生来电，可能怀疑/不耐烦/随口应答 |
| 拾音 | 近讲麦 | 电话链路 + 环境噪声 |
| ASR 错误类型 | **表层**：语气词、重复、断句、回改 | **含内容销毁**：「點證明你唔係呃人嘅」→「点进营，你有细节整改。」 |
| 清理目标 | **可读性**（去口水词/补标点/分段） | 意图可判性 |
| 项目自己的证据 | Type4Me 的 Quick Mode **直接绕过 LLM** 保延迟；Voice Polish 的清单全是表层现象；<br>VoxType 的 LLM 校正**默认关**、且需先开标点；<br>**akang 明确反向**——「avoiding the extra delay of a separate ASR-to-LLM pipeline」，<br>用单一 Realtime omni 模型读音频 | —— |

**结论：校正层治的是表层，我们的病有一部分是内容层。表层能治的部分（去口水词/补标点）
对本产品无价值——我们不需要可读的文字，我们需要能判意图的文字。**

**五条路全部测完，排序如下：**

## 11. ⭐ V-5 验证通过：「低置信度 → 显式澄清」这条路成立

**待验前提**（可证伪）：*存在一个可观测信号，能把「判对了」与「判错了」分开。*
若不存在（模型在损坏输入上"自信地错"）→ 这条路与前五条同样判死。

样本：**65 条已标注转写**（10 句 × 词表 3 档 × 本地/云端两后端，去重后），
同一步骤上下文、同一份 12 选项表。三个候选信号同台比较。

### 11.1 信号 A（概率间距 margin）——有效，且零成本

`margin = logprob(top1) − logprob(top2)`，**不依赖归一化假设**（V1-03 已证 logprob 未归一化），
只用作序数信号。**它就在判定调用本来就会返回的 logprobs 里 → 零额外调用、零额外延迟。**

工作曲线（分四位，左=最不确定 → 右=最确定，格式 `[区间]错/总数`）：

| 模型 | 最低位 | 次低位 | 中高位 | **最高位** |
|---|---|---|---|---|
| 4B | [0.00,0.38] **13/16 错** | [0.38,0.75] 11/16 | [0.75,4.25] 9/16 | [4.75,6.62] **2/16** |
| 9B | [0.38,1.00] **14/16 错** | [1.00,3.00] 10/16 | [3.00,4.25] 6/16 | [4.25,5.88] **0/16** |

**单调，且最高位近乎无错**。中位数分离：4B 对的 4.50 vs 错的 0.50（9×）；
9B 对的 4.25 vs 错的 1.06（4×）。

**推测机制**：margin 实际在追踪**文本质量**——干净文本 → 高 margin 且判对；
损坏文本 → 低 margin 且判错。**这恰恰是我们要的行为**（该澄清的正是文本坏掉的那些轮）。

### 11.2 信号 C（模型选「其他」）——精确率 100%，但只在 9B 上出现

| 模型 | 选「其他」轮数 | 其中判错 |
|---|---|---|
| 4B | **0/65**（内建不确定出口完全不用） | 0 |
| 9B | **7/65** | **7（100%）** |

9B 一旦选「其他」，**必错**。作信号零误伤，但召回低（7/30）。

### 11.3 信号 B（模型自陈「你能不能确定」）——**无效**

另发一次 noul 问「只看这句话，你能不能确定客户意图」：

| 模型 | 对的 中位 | 错的 中位 |
|---|---|---|
| 4B | 0.47 | **0.47（完全相同）** |
| 9B | 0.88 | 0.78（曲线近乎平坦：11/8/6/4/1） |

**模型无法内省自己的不确定**，而且它要多花一次调用。→ **弃用。**
（干净的负结果：**logits 比模型自己说出来的更知道它不知道。**）

### 11.4 组合规则与实际代价

**规则：`margin ≤ 30 分位` OR `选了「其他」` → 本轮改走显式澄清，不执行判定结果。**

| 模型 | 触发 | 捕获错误 | 误伤正确 | 精确率 |
|---|---|---|---|---|
| 4B | 21/65 | 16/35 = **46%** | 5 轮 | 76% |
| **9B** | 21/65 | **19/30 = 63%** | **2 轮** | **90%** |

**9B 是最佳底座**：触发 21 轮（占全体 32%）里 19 轮本来就在错，只搭上 2 个正确轮。
即 **约 32% 的轮次会听到一句澄清，换来 63% 的判定错误被拦下，代价是 2/35 的正确轮**。
（组成：仅 margin 触发 14 轮、仅「其他」触发 7 轮。）

**这与前五条路的根本差别**：热词 / 音学校正 / 小模型校正 / 语义直判 全部是"更努力地听懂"，
在**信息已销毁**的输入上无解；本条**不试图听懂，而是承认听不懂并改走修复动作**——
它要的不是信息，是一个可观测的「我不知道」信号，而这个信号存在。

### 11.5 必须说清的四条限制（否则这条验证不成立）

1. **样本多样性只有 10 句**：65 条是 10 句 × 3 档词表 × 2 后端**扩展出来的**，不是 65 个独立场景。
   margin 分布可能是**句级特异的**。→ **必须在更大的真实通话标注集上复验**（当前唯一的关键缺口）。
2. **30 分位阈值是在这批数据上事后选的** → **过拟合风险**。生产阈值必须在**留出集**上重新拟合。
3. **margin 未标定**（V1-03）：这里只用它的**序数**性质，实验设计刻意不依赖标定，
   所以结论不受 V1-03 影响；但**不能把 margin 当概率解释**（不能说「margin 4.5 = 95% 把握」）。
4. **本轮测的是「能不能识别该澄清」，不是「澄清之后有没有变好」**。
   后者（澄清轮的客户回应、通话是否走回正轨）**未测**，属下一阶段。

## 13. V-6/V-7 复核（2026-09-21 续）+ SemIf 对标

用户三点提问触发的复核：① 回复生成到底慢不慢；② 校正层提示词自相矛盾（批评成立）；
③ SemIf 对标 LAY A。

### 13.1 V-6 回复生成延迟：**回复不慢**，瓶颈不在生成

生产形状（静态 system 183 token + 变化一句，暖前缀缓存），拆三段量：

| 模型 | TTFT（max_tokens=1） | 整句回复（max_tokens=40） | 逐 token 解码 |
|---|---|---|---|
| **4B** | **中位 152ms** | **中位 585ms** | **15.3ms/token ≈ 65 token/s** |
| 9B | 中位 326ms | 中位 1145ms | 21.2ms/token ≈ 47 token/s |

**结论：4B 生成一条 15 token 的粤语回复 = TTFT 152ms + 230ms 解码 ≈ 380ms。这不慢。**
「一轮 ~1s」的体感里，生成只占一小部分——**其余在 endpointing 等待（0.45s）、ASR 解码（~250ms）、
TTS 首包、以及走到 LLM 之前的那些环节**。

**一个对架构有利的推论**：typed decision 的延迟（176ms）与回复自身的 TTFT（152ms）**同量级**，
因为两者都是 prefill 主导。→ **加一层判定 ≈ 多付一次 prefill，约 150ms，是负担得起的。**

**顺带发现（新）**：4B 在**回复路径**上也把 `<|im_end|>` 字面量吐进 content
（`'好嘅，…我幫你處理。<|im_end|>\n'`）。此前只在 V-4 校正实验里见过（V4-09），
现确认**回复主路径同样如此**。经 raw mlx_lm server 必然出现；**agent 路径是否剥离未验证**——
若未剥离，TTS 会读到这个特殊 token。**列为待查项。**
另：9B 生成的回复质量明显更差（句 1 编造号码「5556」并输出舞台指示「（等佢答）」）→ **9B 不适合做回复生成。**

### 13.2 V-7 校正层重测：用户的方法论批评成立，V-4 结论需**部分修正**

**批评成立**：V-4 的校正提示词既要「还原客户本意」又禁止「编造原文没有的内容」——自败，
它当然只能照抄。本轮把校正层做「对」，三个变体对照（都由 4B 执行）：

| 变体 | 意图命中 | 平均保真（vs 源句） | 平均贴合（vs 转写） |
|---|---|---|---|
| 基线（不校正） | 6/10 | 0.42 | 1.00 |
| L1 保守（= 上一版） | 6/10 | 0.61 | 0.60 |
| L2 宽容（允许按情境推断） | **6/10** | 0.47 | 0.45 |
| **L3 词表约束（推断 + 用词落词表）** | **7/10** | 0.47 | 0.48 |

**逐句核对 L3 那 +1 是真的还是运气**：

| 句 | 源句 | 转写 | L3 还原 | 判定 |
|---|---|---|---|---|
| 9 | 你哋查唔查到我個單號 | 你哋有冇呢？上到我个**单后**。 | 你哋有冇呢個**單號**？ | ✅ **真修复**（单后→單號），意图由错转对 |
| 2 | 點證明你唔係呃人嘅 | **点进营**，你有细节整改。 | **點進官網**，你有詳細整改。 | ⚠️ **半编造**（進營→進官網，原文没提官网），意图恰好对了 |
| 10 | 你哋個**倉**喺邊度㗎 | 你哋个**钱**喺边度噶？ | 你哋個**單號**喺邊度？ | ⚠️ **名词换错**（倉→單號），但「喺邊度」保住了，意图靠它对了 |
| 6 | 仲有咩好講呀你話我知 | 仲有咩好讲呀？你望我知。 | 「你唔係要咩單號，唔係要咩運單…」**退化重复** | ❌ 保真 0.02，词表约束把模型带进循环 |

**修正后的判定**：

- **V-4 的「净价值 0」要改成「不是零，但增益在噪声内」**：L3 7/10 vs 基线 6/10，
  **n=10 上差一例，不构成显著**。而**正确的提示词形态是「词表约束」不是「允许自由推断」**
  （L2 宽容 6/10 = 基线，白付一次调用还掉了保真）。
- **校正层确实提高了保真**（0.42 → 0.47~0.61），说明它真的把文本改得更接近源句了；
  **但意图准确度没有跟着走**——因为剩余错误里有一类是**任何校正都救不回的**（见下）。
- **句 4「我已經嬲咗好耐喇」（表达愤怒）在全部变体（含基线、含 clean）都判成「表达不耐烦」**——
  **第三次独立复现**（V4-08、V-7 基线、V-7 三变体）。这条与 ASR 无关，是选项表区分度极限，确认为独立待修项。
- **代价**：多一次模型调用 + 延迟；且 L3 会产出退化重复（句 6）→ **必须有输出长度与重复护栏**。

**对你那句话的回答**：**「先可读性、后意图可判性」这个次序是对的**——
数据上保真确实升了（0.42→0.61）。**但升了可读性之后，意图只从 6 涨到 7**，
因为剩下那部分句子的信息不是"读起来乱"而是"已经没了"。**所以次序对，天花板仍低。**

### 13.3 SemIf 对标 LAY A：**结论反转，它比 LAY A 更贴我们的处境**

SemIf（前身即 **OpenJev**，MIT，独立研究项目，声明与 TypeSafe 无关）：

| 项 | SemIf | LAY A | 对我们的意义 |
|---|---|---|---|
| 接口 | 运行时给 criteria/options，**读原生 option logits，不采样答案 token** | 运行时给 criteria，读 `[MASK]` 位打分 | 同形 |
| 解决的问题 | 「chat model 花时间生成文本，软件又立刻把它解析成 if 语句」 | 同 | **正是我们 L4/L5 的病灶** |
| **Apple Silicon** | **有原生 MLX 后端** | 无 MLX 路径，只能 PyTorch | **⭐ 决定性差异** |
| 模型 | Qwen3-0.6B / MiniCPM5-2B / **Qwen3.5-4B** / Qwen3-Reranker-4B | ModernBERT-large / mmBERT-base | **Qwen3.5-4B 就是我们这颗** |
| 延迟 | 直接 typed logits **1.023s / 0 output token**；自回归 JSON array 5.332s / 111 token → **5.2×** | T4 32.8ms、CPU 193–464ms | 我们自测 4B 同形判定 **176ms**（暖前缀）已优于其公开数 |
| 复用 | fresh 2.33 → 串行前缀 10.75 → **并行后缀 20.03 decisions/s** | 未提 | **同一份长状态预取一次、对多条 criteria 分支** → 与我的「按步静态前缀」发现同源，且**把它量化了** |
| 准确率 | 浏览器阶梯 balanced：0.6B 0.440 / 2B 0.686 / **Qwen3.5-4B 0.813**（TypeSafe 子集 0.845）；公开 Jev 0.883 | typed-decisions 0.766 | 有可对照的绝对刻度 |
| 保留 | 「fast reuse paths are experimental」；复用改了 777 个 argmax 里的 5–6 个 | 需微调、非英语弱 | 复用路径**本身会改变结论**，须验证 |

**结论：SemIf 应当是 L4/L5 落地的候选实现，而不是我手搓。** 理由三条：
① **有 MLX 后端**（LAY A 的死穴它没有）；② **用的就是我们的 Qwen3.5-4B**，且给了可对照准确率 0.813；
③ 它的「shared-state aware / 一条长状态预取一次再对多条 criteria 分支」正是我实测出的
「候选清单必须进按步静态前缀」，**并且它把复用收益量化到 20 decisions/s**——
意味着**在一条会话前缀上跑多条 typed 判定几乎免费**（意图归属 + 是否拒绝 + 是否报号 + 情绪强度
一次批量问完），这对 V-5 的澄清闸是直接的放大器。

**⚠️ 必须验证的一条**：它自陈复用路径「experimental」且**改了 777 个 argmax 里的 5–6 个**——
即**加速会轻微改变结论**。我们的 V-5 澄清闸依赖 margin 的序数性质，
若复用会扰动 margin，闸门阈值需要重拟。**列为 SemIf 落地前的必测项。**

## 14. T2/T3 实测：SemIf 上机（本机 MLX + 我们的 4bit 模型）

装法：**独立 scratch venv** `/tmp/semifvenv`（`uv venv` + `uv pip install -e '.[mlx]'`），
落 `mlx 0.32.2` / `mlx-lm 0.32.0`(指定 commit) / `torch 2.10.0` / `transformers 5.17.0`。**不碰项目 `.venv312`。**
（磁盘只剩 25Gi，故**不下载 8GB 官方 BF16 版**，直接用我们自己的 4bit 模型——反而能同模型同任务直接对照。）

门槛校验（源码实测）：`load_model` 强制 `config.model_type == "qwen3_5"` 且**不许对已量化源再做内存量化**。
我们的 `avan-ag/Qwen3.5-4B-Uncensored-MLX-4bit` 两条都过（`model_type: qwen3_5`、已 4bit affine），
故**不传 `--mlx-bits`**，用源精度。

### 14.1 T2 成绩：准确率持平，但**概率是归一化的**（V1-03 的解法）

| | SemIf | 手搓版（同模型/同 12 选项/同上下文） |
|---|---|---|
| clean 命中 | **9/10** | 9/10 |
| asr 命中 | **4/10** | 5/10 |
| **概率和** | **1.0000（归一化 ✓）** | **>1（未归一化，V1-03）** |
| forward 中位 | 891ms（**冷 prefill，454 token**） | 176ms（**暖前缀缓存，253 token**） |
| 溯源 | `prompt_sha256` / `input_ids_sha256` / `prompt_version` / artifact 哈希 | 无 |

**准确率持平**（差 1 例，n=10 不显著）。**延迟那个 5× 差距是口径不同，不是它慢**：
它每行都是**冷 prefill**；我手搓的 176ms 是**暖前缀**。按冷启动同口径折算
（我测过冷启 665ms/253 token → 454 token 约 1190ms），**SemIf 的 891ms 反而更快**。

**⭐ 最有价值的一条**：SemIf 的 `probabilities` **和恒等于 1**。它不是我那样去信服务端的
`logprob` 字段，而是**自己取每个选项 token 的 logit、自己做 softmax**（`core.softmax`）。
**这直接解决 V1-03**——我们不需要"标定过的置信度"，只需要**正确的归一化**，
而正确归一化是自己算出来的，不是服务端给的。**这是可以立刻搬回手搓版的一个改动。**

**但归一化 ≠ 可信**：asr-5 判错时 P=0.869、asr-1 判错时 P=0.785——
**在损坏输入上它同样过度自信**（与 V1-14 同族）。

**另一条**：它的失败模式与手搓版**不同**——SemIf 在 asr 臂上三次误判到「表达愤怒」
（asr-1 诈骗质疑 / asr-5 索要主管电话 / asr-10 问仓库位置）。**「表达愤怒」这个选项在吸引损坏文本**，
与 V4-08/T4（愤怒 vs 不耐烦）同源 → **该选项的区分度问题比原先估计的更严重，它污染的不止句 4。**

### 14.2 T3 复用：**答案安全，但我们的形状拿不到提速**（根因已定）

复用保真度（同 state 多 criteria，`/tmp/semif_t3.jsonl` 6 行）：

| 对比 | argmax 一致 | 最大概率差 |
|---|---|---|
| direct vs serial | **6/6** | 0.0224 |
| direct vs shared | **6/6** | 0.0224 |

生产形状（T2 的 20 行，共享 STEP_CTX 前缀 + 不同转写，跑 serial）：

| 模式 | clean | asr | forward 中位 |
|---|---|---|---|
| direct | 9/10 | 4/10 | 891ms |
| serial | 9/10 | 4/10 | **903ms（无提速）** |

**argmax 一致 20/20**，最大概率差 0.0388。
→ **复用不会改答案**（比它 README 自陈的「777 个 argmax 改 5-6 个」在**我们的形状上**更干净），
但**也拿不到任何提速**。

**根因（`direct_messages` 源码实测）**：SemIf 的提示词布局是

```
[system: DIRECT_SYSTEM（静态）]
[user: {"evidence": <state=上下文+口语>, "criterion": <问题>, "options": [...12 项描述]}]
```

**变化字段 `evidence` 在最前面**，静态的 `criterion + options`（约 350+ token，占 454 的绝大部分）
**全在分歧点之后** → 跨行前缀复用在结构上不可用。

**这正是我在 V1-08 测出来的同一件事的反面**：我把候选表放「按步静态」前缀、变化的口语放最后 → 176ms；
SemIf 把静态部分放最后 → 891-903ms。**它的设计目标是「一条 state 预取一次、分支多条 criteria」，
而我们是「一条 criteria、多条 state」——形状相反。**

### 14.3 T2/T3 结论：**不要整体采用 SemIf，但要搬它三样东西**

| 维度 | SemIf | 手搓版 | 采用谁 |
|---|---|---|---|
| 概率归一化 | ✅ 自己算 softmax | ❌ 信服务端 logprob（和>1） | **搬 SemIf 的做法**（解 V1-03） |
| 选项打分 | 每选项独立 token + **tokenization 边界校验**（`prompt+letter` 必须恰好是 `ids+[slot]`） | 字母标记，无边界校验 | **搬它的边界校验** |
| 溯源 | prompt/input sha256 + 版本 + artifact 哈希 | 无 | **搬它的做法**（可审计） |
| **前缀复用（生产形状）** | ❌ 布局挡住（891-903ms） | ✅ **176ms** | **留住手搓版的布局** |
| 复用（同 state 多 criteria） | ✅ 支持且不扰动 | 无（但可自己批量化） | 视需要 |
| 准确率 | 持平（9/10、4/10） | 持平（9/10、5/10） | 平手 |

**一句话**：**SemIf 的"正确性工程"值得抄（归一化 + 边界校验 + 溯源），
但它的提示词布局与我们的延迟预算不兼容，整体采用会把判定从 176ms 拖到 ~900ms。**

## 12. V-1 结论与下一步

**已可定论的四条**：

1. **架构成立且零新依赖**：用 mlx_lm 原生 `logprobs` 做 prefill-only typed decision
   （`noul`/`choice`/`score`），**不需要 LAY A、不需要第二个运行时**。
2. **收益来源要重新表述**：不是"换个更快的模型"，而是**把生成式判定换成判类型判定**——
   9B 即使 413ms，对比现状（生成式 judge / `timeout=20s` / 迟一轮 / pending+TTL+store 守卫）
   仍是几十倍提速且同轮同步。**`docs/A_LINE_LOGIC.md` §10.4 的「迟一轮」结构洞具备消除条件。**
3. **两模型按用途分工，不是二选一**：4B（176ms，判据内）做**必须同步**的判定；
   9B（413ms，更准）做**可以多花 400ms** 的判定。分工线由「这个判定的延迟预算是多少」决定。
4. **两条硬实现约束**：① 候选清单进「按步静态」system 前缀（V1-08，176 vs 348ms）；
   ② 标记用单 token 符号、按 token id 映射（V1-02/V1-10）；③ 阈值逐问题经验拟合，不信自报置信度（V1-03）。

**仍待补的五条**：

- **V1-11 的近同文坍塌**：机制未清（`v1f` 显示破缓存能救，`v1g` 显示生产形状本就没事）——
  需要一个隔离变体把「缓存」与「近同文上下文」分开。**虽然不污染生产形状，但它是唯一没查清的异常。**
- **准确率放大样本**：n=7 定不了 4B/9B 优劣 → 用 V-4 的真实挖掘语料（L-① 漏网轮 + QA 问法）扩到 50–100 例。
- **V1-03 量化对照**：8bit 4B 的 logprob 是否归一化、是否更锐 → 空闲端口起第二实例对比。
- **多 token 选项打分**：本轮用单 token 标记绕开，需测「选项原文前缀打分」方案（更贴近运营写法）。
- **V1-08 边界**：步骤切换时静态前缀会变 → 步骤切换那一次的冷启成本要测
  （`prompt-cache-size 128` 可能同时保住多步前缀）。

## 15. 延迟真相：打断/连说两句下的「生成变慢」归因（V-8~V-13）

**用户诉求（2026-09-20）**：「我们 llm 生成回复的速度，如果用户打断情况下、比如连说两句，
我们的生成时间会直接拉到非常长——这个也要检查探索一下。」

**做法**：零代码。① 先读 mlx_lm server 调度面源码定假设；② 在 :1235 上跑受控探针
（`/tmp/v9_cancel_block.py`、`/tmp/v11_prod_shape_cancel.py`）；③ 从 `agent.log`
全量回捞真实通话做相关性（`/tmp/v10_ttft_fit.py`、`/tmp/v12_log_correlation.py`）。
6 个服务 PID 全程不变，运行时零改动。

### 15.0 结论先行

1. **慢的不是「生成」，是「首 token 之前那一段」。** 2571 条真实样本反算：首 token
   之后的耗时 p50=**384ms**、p90=825ms；**TTFT 占整轮 LLM 耗时的中位 74%**。纯生成速率
   p50=**63.9 tok/s**（与 V-6 实机 65 tok/s 一致）；每轮生成量中位只有 23 token。
   → **「生成时间拉到非常长」这个现象是真的，但归因错了：要治的是 TTFT。**
2. **TTFT 的主项是「每轮新拼接的尾部」**，不是取消、不是生成。拟合
   `TTFT ≈ 285ms + 未缓存token/586`（586 tok/s ≈ 文档记的 0.6k tok/s）。
   生产每轮未缓存 **p50=254 / p90=724** token → 这一项就吃掉中位轮 TTFT 的 60%。
3. **打断确实有代价，但是重尾不是普遍规律**：真实通话里打断后紧接一轮 TTFT
   **中位 +0ms**、均值 +216ms、**p90 +1520ms、最大 +6662ms**（n=265）。中位看不出问题，
   用户感受到的「非常长」落在尾部。
4. **真正的放大器是兜底阈值与看门狗，不是模型**：`LLM_FIRST_TOKEN_TIMEOUT_S` 默认 **2.0s**，
   而 **TTFT>2000ms 的轮占 19.3%**——**闸门设在了正常分布的第 80 分位上**。慢轮触发兜底链
   （兜底句先出 → 原流 drain 8s → 晚到补答 → 4s 看门狗 force-interrupt）后，
   **已经生成的正确答案会被掐掉**：48 次晚到补答里 **17 次（35%）被同轮看门狗掐掉**，
   客户听到的是兜底句而非答案。

### 15.1 度量口径修正：`tps` 是复合值，不是吞吐

`agent.log` 的 `tps=` 取自官方 `LLMMetrics`，而官方口径是
（`livekit/agents/llm/llm.py:389,409`）：

```python
duration = time.perf_counter() - start_time          # start_time = 请求发出
tokens_per_second = usage.completion_tokens / duration
```

**`duration` 含 TTFT**。所以 `gen=20 tps=5.1` 反推 duration=3.92s，而该轮 `ttft=3.602s`
→ 首 token 之后 20 个 token 只花了 0.32s（≈62 tok/s）。**低 tps 与高 TTFT 是同一件事的
两种写法，不是两个独立信号。**

> ⚠️ **纠正**：`AGENTS.md` 与延调脚本把 `tps` 当吞吐读数用（「回复慢半档」类判读）。
> 它其实是 `gen/(ttft+gen_time)`。**判读回复速度要看 TTFT**，`tps` 只可用于反推总耗时。

### 15.2 V-9：取消是否阻塞队列——第一轮假设被否

源码面先确认了三条事实：
- `mlx_lm/server.py:1592` `finally: ctx.stop()` 是**唯一**的取消钩子，只在 HTTP handler
  的 SSE 循环退出时执行；handler 退出的前提是 `wfile.write` 抛错。
- 生成本体在后台批处理线程 `_generate()`（`:708`）里跑，与 handler 是否 drain 无关。
- `_should_stop` 只在 prompt/gen 响应点被检查（`:881`、`:931`）。

假设 H-cancel：**客户端断开后请求继续解码到 max_tokens（生产 160），占据批槽拖慢下一轮。**

探针实测（满缓存形状，基线 156ms）：断开后探针 TTFT **261ms，惩罚仅 +105ms**；
且惩罚**不随被取消请求的 `max_tokens` 缩放**（32/160/400 → 264/255/270，平的）。
→ **取消是有效的，没有空转。H-cancel 在第一版形状下被否。**
并发侧探针（T5）：两个请求同时发，两个 TTFT 都是 302ms、墙钟 453ms
→ **连续批处理确实在工作**（`is_batchable` 为真：`ArraysCache` 有 `merge`，`:702`）。

### 15.3 V-11：修正基线后，取消的代价成立——取决于取消点

**V-9 有两个缺陷**（本轮自查发现）：(a) 探针请求满缓存（0 未缓存），而生产是 ~500 未缓存
→ 测不到 prefill 与取消的交互；(b) 基线用「孤立请求」，而取消组里「前面刚跑过一个请求」
本身就有成本 → 会把前序成本误记成取消惩罚。

重做（生产形状 = system 静态 + 用户轮 ~281 未缓存，`max_tokens=160`，n=6）：

| 条件 | 探针 TTFT 中位 | 相对孤立基线 |
|---|---|---|
| C1 孤立生产形状请求 | 673ms | — |
| **C2 前一请求读到底（公平对照）** | **667ms** | **−6ms** |
| C3 **prefill 中**取消（120ms 断开，首 token 前）→ 探针 | 751ms | +77ms |
| C4 **首 token 后**取消（读 3 块断开）→ 探针 | **1111ms** | **+438ms** |

**C2 是关键对照：前一个请求正常跑完，对下一轮零成本（−6ms）。** 所以 +438ms 是
「取消」这个动作本身的代价，不是「前面跑过请求」。C4 六次读数 1103–1117，紧到不像噪声。

→ **修正后的结论：打断确实会让下一轮 TTFT 变长，幅度取决于打断发生在哪一相位——
首 token 之后打断 ≈ +438ms，prefill 中打断 ≈ +77ms。**
机制未完全定位（见 15.6 待办）：候选是「已取消序列在批里残留到下一检查点」
与「prompt cache 插入被跳过（`:923` 只在 `finish_reason` 时插）」。

### 15.4 V-10：生产 TTFT 的全量分解（2133 条样本 / 708 通话）

```
[1] TTFT  ms:  p10=417  p50=850  p90=2344  p99=6581  max=11584
    未缓存 token: p10=70  p50=254  p90=724   p99=1519  max=2131
[3] 地板（未缓存<=60, n=69）TTFT: p50=349ms
```

按未缓存量分桶看 TTFT 中位，两点定斜率：

- 未缓存 100 → 456ms；未缓存 1000 → 1993ms
- 斜率 = 1537/900 = **1.708 ms/token → 586 tok/s**；截距 = **285ms**

拟合式 **`TTFT ≈ 285ms + 未缓存token / 586`**，与地板实测（预测 387ms / 实测 349ms）吻合，
与 `p50` 实测（预测 719ms / 实测 850ms）吻合。

**含义**：`285ms` 是框架+HTTP+队列的固定底噪；`586 tok/s` 是 prefill 硬墙。
**每轮新拼接的尾部（未缓存 p50=254、p90=724 token）是 TTFT 的第一大项。**
大桶（未缓存 1200+）实测 4408ms 高于预测 2847ms → 大 prefill 有额外劣化
（分块 prefill 与并发抢占），单独待查。

### 15.5 V-12：真实通话里「打断→下一轮」的相关性

全量 agent.log：828 通话、2133 条 TTFT、**打断事件 557 次（298 通话出现过）**。

| 指标 | 值 |
|---|---|
| 打断后紧接一轮 相对本通话中位 | 中位 **+0ms** / 均值 +216ms / **p90 +1520ms** / 最大 +6662ms（n=265） |
| 打断后那一轮 TTFT 中位 | 1001ms（同批通话正常轮中位 955ms） |
| TTFT≤1000ms 的轮 | 1310 |
| TTFT>2500ms 的轮 | 256 |

高 TTFT 通话组（n=98）vs 低 TTFT 通话组（n=593）的伴随事件出现率：

| 通话组 | 有看门狗 | 有首token超时 | 有补答 |
|---|---|---|---|
| TTFT>2500ms | 18% | 15% | 16% |
| TTFT≤1000ms | **1%** | **0%** | **0%** |

→ 高 TTFT 与兜底链**强耦合**。注意因果方向：看门狗是「没音频」的**后果**，不是原因；

### 15.6 放大器：兜底阈值低于正常分布

- `LLM_FIRST_TOKEN_TIMEOUT_S` 默认 **2.0s**（`livekit_plugins.py:488`），
  **TTFT>2000ms 的轮占 19.3%** → **每 5 轮有 1 轮的正常 TTFT 会被判成超时**。
- 看门狗 `BOK_RESPONSE_WATCHDOG_S` 默认 **4s**（`agent.py:753`）。`commit→音频` =
  eou(~500ms) + TTFT + TTS首音(~300ms)；TTFT=2344ms（p90）时已用 3144ms，
  只剩 856ms 余量 → **TTFT 超过约 3.2s 的轮（约 5%）看门狗必然误触发**。

触发后的级联是**净损失**：`force-interrupt` 清掉 speech 队列 → 已生成的答案不播 →
改念兜底句。实测（call-3afff7c4，逐行证据）：

```
LLM_TTFT_MS 3602 ... gen=20 tps=5.1
PERCEIVED_MS total=5342 (eou=1160 llm=3601 tts=581)
LLM_LATE_ANSWER source=drain chars=28 — 补答          ← 正确答案已经出来了
[watchdog] no assistant audio 4s → force-interrupt + ack
MINIMAX_BIDI_PERF sentences=0 canceled=1 (interrupted) ← 补答一个字都没播出去
TTS_CACHE hit=1 chars=21                                ← 客户听到的是兜底句
```

全量统计：**晚到补答 48 次，其中 17 次（35%）被同轮看门狗掐掉**；
`sentences=0 canceled=1`（播报轮零句被取消）**395 次**。
（注意：零句取消不全是缺陷——用户抢话时 AI 本就该停；缺陷面是「答案已到仍被掐」那 17 次。）

## 16. L3 落地：晚到补答被看门狗掐掉的根因与修复（V-14）

### 16.1 证据：不是「慢」，是「拆弹信号缺失」

§15.6 观察到 17 次「补答已到仍被掐」。交叉表把它钉死（按轮内首个 `TTS_CACHE hit=` 行分组）：

| | 被看门狗掐 | 存活 |
|---|---|---|
| TTS 缓存 MISS（合成腿） | **17** | 23 |
| TTS 缓存 HIT（命中腿） | **0** | 3 |

现场 2 是决定性的——**音频早已就绪，仍被掐**：

```
LLM_LATE_ANSWER source=drain chars=43 — 补答
TTS_CACHE hit=0 chars=43 / TTS_CACHE hit=0 key=a6cb692747 chars=43
PERCEIVED_MS total=2880 (eou=483 llm=2074 tts=323)   ← TTS 首音仅 323ms
TTS_CACHE stored=1 ok=1 key=a6cb692747 bytes=430090   ← 整段音频已合成落盘
[watchdog] no assistant audio 4s after commit → force-interrupt   ← 照掐
```

### 16.2 根因：`_say_script` 两条腿都不产出首音频回调

看门狗唯一的拆弹口是 `tts_provider.add_first_audio_listener(...)`（`agent.py` 装配点），
它只认 TTS 图的首帧。而晚到补答走 `_late_answer_say → _say_script`，两条腿都绕开了它：

| 腿 | 实际路径 | 是否 fire 首音频回调 |
|---|---|---|
| `_say_script` **命中** | `cache.lookup` → `session.say(text, audio=frames_aiter(...))` **直接喂 PCM，完全绕过 TTS** | ❌ 结构性不可能 |
| `_say_script` **未命中** | `session.say(text)` → `CachedTTS.synthesize`（也 miss）→ `_StoreChunkedStream` | ❌ 该类**不收** `on_first_audio` 参数 |
| （对照）`CachedTTS.synthesize` 命中 | `_CachedChunkedStream` | ✅ 2026-09-17 RC2 已修 |

**直念族其余 14 处调用点靠「出声前显式 `_cancel_response_watchdog()`」绕过了这个盲区，
唯独补答投递点没有。** 这就是 17 次净损失的成因。

### 16.3 一次被推翻的修复方案（记录在案）

**第一版修复（错误，已还原）**：给 `_StoreChunkedStream` 补上 `on_first_audio`，
让 `CachedTTS.synthesize` 两条分支对称 fire。

**为何是错的**：`synthesize()` 不是补答专用——**`_filler_backfill`（后台补物化垫话）
走的正是 `tts_provider.synthesize(text)`**。让它无条件 fire，后台合成就会把
**在途轮**的看门狗误拆掉，掩盖真正的「零音频」故障。本分支 `_FirstAudioTTS` 的
docstring 早已写明这条边界（"在此 fire 会拿后台合成误拆在途轮"），我第一版违反了它。

**发现的契机**：该补丁误落在主仓而非本会话 worktree，核对基线时发现
worktree 比主仓多一整个 `_FirstAudioTTS` 类（本会话早前 D2 提交），进而查到
docstring 的边界声明。**若没这条目录事故，错的补丁会直接进主干。**

### 16.4 已实施修复

### 17.1 V-13 定案：取消代价矩阵（修掉探针 bug 后复现）

| 条件 | 取消生效 | 探针 TTFT 中位 | 极差 | 相对基线 |

## 19. §16 修复的真栈复测：复现成功，但未干净隔离出修复的作用

§18 的阻塞（worker 端口被并行会话 monitor 占）**已绕开而非解除**：仓库自己留了逃生口，
不必动对方的进程。本轮据此做了真栈 A/B。

### 19.1 绕开方式（零接触对方进程）

`apps/agent/agent_runtime/agent.py:5311-5313` 注释写明的设计：`BOK_WORKER_PORT` 可覆盖，
「单机多栈并存（并行会话/多 worktree 验收）时错开端口」。据此：

- 我自己的 worker 起在 **:8091**（默认 8081 零漂移，不动）；
- env 由 `bok.py` 的 `_agent_worker_env()` 构造（避免手搓漏掉模型路径/凭据），cwd 与
  PYTHONPATH 锁主仓并加泄漏核验（PYTHONPATH 出现 `work-session-` 即中止）；
- **归属靠日志文件判定**：我的 worker 日志写 `/tmp/retest_worker*.log`，对方的写
  `app_data/logs/agent.log`，同一通只会在其中一处出现。**这一步不可省**——第一次跑
  就落在了对方的 worker 上（agent.log 38 处 / 我的 0 处），差点把别人的代码当成自己的证据。
- 全程未 kill/重启对方的 monitor（pid 48673 与三个 worker 端口自始至终未动）。

**发现一个仓库缺陷（本轮实证）**：`BOK_WORKER_PORT` 是**双重半接线的**——
`_worker_specs()` 里 `"port": 8081` 硬编码（`bok.py serve`/`monitor` 用不上它），
`worker_port_singleton_guard(8081, "agent")` 也硬编码（worker 自己一查 8081 被占就
`SystemExit(0)`）。所以那条注释承诺的「单机多栈并存」在 8081 被占时**走不通**；
实际可用的姿势是再加 `BOK_WORKER_PORT_GUARD=0`（守卫 docstring 本就标注为诊断口）。
三处硬编码是同一类问题，值得收口成单点。

### 19.2 两次无效尝试（都靠自查拦下）

| 尝试 | 现象 | 为何无效 |
|---|---|---|
| 第 1 次 | E2E PASS，但我的日志无该通话 | **落在对方 worker 上**——归属判定拦下 |
| 第 2 次（timeout=0.05s） | **A/B 两臂读数完全相同** | timeout 早于垫话 500ms 延迟 → 永远走 `FALLBACK_TEXT` 分支 |

第 2 次的「两臂全等」是关键红旗：**读不出差异时，先怀疑实验没打到靶，而不是「修复无效」。**
根因随后查清：**`FALLBACK_TEXT` 分支会自我拆弹**——那句道歉词进 LLM 流、经 TTS `stream()`
播出，首音频回调 fire → 看门狗在该轮被拆。这从机制上解释了代理 A 那条
「suppressed 17/20 被掐 vs fallback 4/21」的分裂：**只有 suppressed 分支不产出任何文本、
因而永不触发首音频回调、看门狗才武装得到开火的那一刻。**

### 19.3 有效 A/B（进对了 suppressed 分支）

参数：`BOK_FILLER_DELAY_MS=100 LLM_FIRST_TOKEN_TIMEOUT_S=0.5 BOK_RESPONSE_WATCHDOG_S=1.5
BOK_RESPONSE_WATCHDOG_FILLER_EXT_S=0`（关顺延，否则垫话把闸推后 2s 盖过观察窗）。

| 判据 | B 臂（摘掉修复） | A 臂（含修复） |
|---|---|---|
| 进入 `suppressed` 分支 | 1 | **6** |
| **`[watchdog] no assistant audio`** | **1** | **1** |
| `force-interrupt` | 1 | 1 |
| `sentences=0 canceled=1` | 1 | （多来自用户抢话，非看门狗） |

**B 臂复现了历史签名**：suppressed 轮 → 看门狗开火 → force-interrupt → 一条回复零句被取消。
这是**该 bug 的首次真栈现场复现**（此前只有历史日志的统计相关）。

### 19.4 结论：复现成功，隔离失败（如实）

**修复的作用没有被干净隔离**：A 臂 6 个 suppressed 轮里仍有 **1 次**看门狗开火。
原因不在修复而在**实验时间轴**：压缩后看门狗闸（1.5s）常常**早于补答到达**（约 1.2-2.0s），
那一段窗口修复本就救不到（`_cancel` 只在补答投递时执行）。所以两臂都能开火，
只是 B 臂样本太少（1 个 suppressed 轮）看不出比例。

**下一次要怎么设计才干净**（本轮未做）：
1. 先量准 `commit → 补答到达` 与 `commit → 首音频` 两条时间线的实测分布，
   把 `BOK_RESPONSE_WATCHDOG_S` **落在两者之间**（生产里就是这个 ~300-800ms 的窄窗）；
2. 或者按生产值复刻：看门狗保持 4s、刻意把 LLM 拖慢到 TTFT 2.5-3.6s（生产被掐轮的实测区间），
   不要压缩时间轴；
3. B 臂样本要堆到 ≥5 个 suppressed 轮才能比比例。

## 20. 真栈配对 A/B：把修复的作用干净隔离出来（确定性派单）

§19.4 列的三条「下一次」全部做到了，而且换了更硬的路子：**不再赌派单**。

### 20.1 为什么放弃「按日志归属过滤样本」的彩票协议

共享 LiveKit 上同时注册着两个 `bok-voice` worker（并行会话的 :8081 与我的 :8091）：

| 尝试 | 结果 |
|---|---|
| 顺序三连发（09:09-09:15） | 全落对方 worker（我的日志 0 行） |
| 重叠两发（09:19） | 一发落我、一发落对方 |
| 重叠两发（09:23，我重启 worker 后） | **两发全落对方** |

根因是两处硬编码：CP 的 token 路径写死 `agent_name="bok-voice"`（`control_plane/main.py:1466`），
worker 注册名也写死（`agent_runtime/agent.py:5315`）→ 同一个 agent_name 池里由 LiveKit 自行择优，
**脚本侧无法指定**；而且选中谁实测不稳定。彩票协议还有个隐性代价：两臂样本的采集条件
（是否与其他通话重叠）会漂移，正是 V-9 那次「一个实验差两件事」的坑。

### 20.2 确定性装备（三件，两臂完全同构）

1. **worker 注册名 env 化**（临时诊断补丁，收工已 `git checkout` 还原）：`agent.py:5315`
   改读 `BOK_AGENT_NAME`（默认仍 `bok-voice`，零漂移）；
2. 我的 worker 起在 :8091、注册名 `bok-voice-ab`，env 取 `_agent_worker_env()` 的**权威全集**
   （含 `MLX_LLM_BASE_URL`/`MLX_LLM_MODEL` 与判据专线——20.4 那个坑就是漏了它）；
3. 驱动 `/tmp/ab_drive.py`：CP 照旧建对象/人设/通话（turns 照落库），但 **token 自签**
   （不带 `RoomConfiguration` → 不请求 peer 那次派单）+ 自己
   `AgentDispatchService.create_dispatch(agent_name="bok-voice-ab")`；刺激物直接
   `import e2e_multi_turn` 复用其 `TURNS`/`push_and_collect`/`asr_language`
   （逐轮音频与读回断言**逐字节同构**，不引入新刺激物方差）。

→ 两臂落在**同一 worker、同一 env、同一刺激物**上，**只差一行代码**。归属不再需要事后过滤

### 20.3 结果（每臂 2 通 × 3 轮；timeout=0.5s / 垫话 100ms / 看门狗 2.5s）

| 判据 | B 臂（摘掉修复） | A 臂（含修复） |

| LLM API 错误（健康对照） | 0 | 0 |

**核心读数：fires 4 → 0，且 suppressed 4 轮 ↔ fires 4 次严格 1:1。** 这就是隔离——
同样的触发条件（B 臂 4/4 复现），修复把开火清零。§16 的机制解释（suppressed 分支不产出
任何文本 → 永不触发首音频回调 → 看门狗武装到最后）同时被证实：两臂 `FALLBACK_TEXT` 各 2 轮

### 20.4 两处对我自己前文的更正（都靠配对臂拦下）

## 22. 可信修复计划（L1-L5）

按「证据强度 × 收益/成本」排序；每条给改法、预期收益（尽量带本轮实测数）、风险、验证方式。

### L1 晚到补答投递点自拆看门狗 —— **已落地（PR #128）**
- 改法：`_late_answer_say` 出声前 `_cancel_response_watchdog()`（`agent.py:2748`）。
- 收益：受控配对 fires **4 → 0**（suppressed 4 轮 1:1 复现）；§20 即验收。
- 风险：若用户已开新轮，新轮的看门狗会被一并拆掉——与同钩子内 14 处直念族**同一取舍**，
  由新轮自身音频覆盖。**低**。
- 验证：结构测试 `tests/test_watchdog_filler_extend.py::test_late_answer_cancels_watchdog_before_saying`
  （摘掉那行即红）+ §20 真栈配对。

### L2 晚到补答补上出口两道防线（**新发现，未做**）
- 现状：`late_answer_cb` 直投的文本结构性绕过 `_StripTailAnchorStream`/`_RepeatSelfGuardStream`
  （§20.5 代码定位 + B 臂账本实证念出 `【你上一句】「…`）。
- 改法：把锚剥离提成**纯函数**（现逻辑在 `_StripTailAnchorStream._feed` 的流式状态机里；
  常量已单点 `_TAIL_ANCHOR_LABEL = "【你上一句】"`），在 `_late_answer_say` 投递前调用一次。
  复读防线（句级比对）成本更高，建议先加「补答与上一句相似度」打点观测再决定。
- 收益：补答路径（历史 41 次到达）上的念错类缺陷清零。
- 风险：**低**（纯文本变换）；需注意别误伤「客户明确要求重复」的场景——那条走
  `repeat_requested` 分支，与补答路径无交集。
- 验证：纯函数单测（含跨 chunk 边界的锚块）+ 一次 driven call 看 turns 行无锚块。

### L3 兜底阈值与 TTFT 分布错配（**最大杠杆，未做**）
- 现状：`LLM_FIRST_TOKEN_TIMEOUT_S` 默认 2.0s，而实测 TTFT **>2000ms 占 19.1%**（497/2607）；
  进兜底链是整条「suppressed → 看门狗」序列的唯一入口（历史通话级 17/17；控制臂轮级 4/4）。
- 改法：默认抬到 **3.0s**（入口从 19.1% 砍到 **6.8%**，2.8×），或按 §15.6 与垫话延迟联动。
- 收益：掐答案暴露面同比缩小（与 L1 叠加后趋零）；**不**改善 TTFT 本身（那是 L4）。
- 风险：**低**——真死流上道歉句晚 ~1s 出声，但这 1s 由垫话（0.5-2.3s，独立于 LLM 阈值）
  已盖住，用户可感空档不变。**前提是垫话开着**：若 `BOK_FILLER=0`，这条结论不成立，
  改默认时须一并说明。
- 验证：改默认后重跑 `e2e_multi_turn` + `probe_latency_soak`，对比兜底触发率与首声时间。

### L4 TTFT 本身：**先测后改**（未做）
- 事实：TTFT 占 LLM 墙钟 74%；地板 349ms + prefill 582 tok/s（§21 换基复算）。
  §15.4 那 1.5s 超额仍未归因，唯一决定性测量 = **给每轮请求加 `X-Bok-Turn` 头**，
  在服务端把「ctx-ready 等待」与「prefill」在时间轴上分开。

  收益未知，**先测再改**。
- 验证：`X-Bok-Turn` 头落地后跑一轮真实通话，看被掐轮的 ctx-ready 段占比。

### L5 仓库卫生：worker 端口/注册名单点化 + 归因仪表（未做）

## 23. T5/T6/R1 实测：真实集上信号成立但覆盖缩水；选项表合并定案（2026-09-21 收尾）

**一句话**：R1——margin 信号在真实通话轮上仍是单调的错误预测器，门控精确率
4B **98%** / 9B 80%，但捕获率缩到 **39%/36%**（合成集 46%/63%），且 §11.4 的

### 23.3 T5 读数：选项 softmax（4B 进程内精确，一次 forward 取 12 字母 logit）

  78%（合成）**；合成集组合规则新旧同为 90% 精确率。
- **两个落地坑（都会静默出错，必须写进实现规格）**：
  1. mlx_lm 服务端 `top_logprobs` **硬上限 11**（≥12 直接断连，实测 5/10/11 OK、12+ 崩）

### 25.3 新增执行项（并入 P1-P3）

**E1（P1 新增，最高价值）snippet 后置正则轨——A 线**。位置=ASR final 之后、意图判定/QA
匹配之前；语义照 type4me：trigger 去空白后插 `\s*`、仅 ASCII 词边界、caseInsensitive、
用户条目覆盖内置。**为什么它是对「热词不够」的正确补位**：硬混淆（嬲/賠償/單號/倉类）
的错形是**有限且重复的**——词级替换零 LLM、零信息销毁，比 QA 整句字面匹配粒度细、
比 LLM 校正可靠；热词（bias）救不了的词，snippet（确定性替换）救得了。词表来源=
L-① 漏网轮挖掘 + 人工确认（勿自动写全局）。验收：`probe_hotword_ab` 硬混淆句集 +
snippet 轨 A/B；改 ASR/意图链后跑 `e2e_edge_cases`。

**E2（P4→提前）热词准入与泄漏加固**。准入白名单（模型词表内/品牌/术语才进热词，
其余下移 snippet）；**Qwen3 热词泄漏清洗器**（type4me `Qwen3HotwordLeakSanitizer`
现成设计：剥 `Vocabulary:/词汇：` 标签+最长连续热词前缀，命中 ≥2 热词或标签即判泄漏、
用 fallback）——我们已知该现象（AGENTS.md 记载极低内容音频会抄词表），现给防线加
确定性判据。验收：静音探针复测（`probe_fast_speech` 同款刺激）。

**E3（P1 新增）OutputGuard 确定性后验**。对意图判定结果/QA 候选/垫话触发前文本做
后置断言：数字/日期/金额/单号 token 不得被改写、语义否定计数不减、语言不漂移；
拒绝→**回退原文语义照走**（不销毁信息，与我们「宁可退原文」原则同源）。
实现可挂在 QA 快路匹配前与意图判定后两个点。验收：单测（对照 type4me 硬拒绝清单
逐条）+ offscript soak 无回归。

**E4（P1 新增）改口检测规则进话术 verdict**。显式改口标记（不对/算了/改成/应该是/
i mean/sorry）=高置信改口，区间后 token 为准；**「不是 A，是 B」裸对比不当改口**
（除非有显式证据）；「不要改成 X」是真否定必须保留。直接映射到
`FlowController` 的 CONFIRM/UNCLEAR 判定与 WA 累积轮。验收：`test_flow_controller.py`
新增判例。

**E5（P3 新增）B 线术语双轨 A/B**。臂 A=现状（术语进 ASR 热词+MT prompt 槽）；
臂 B=type4me 形态（术语在 MT **前**做正则归一，MT prompt 保持纯净）。判据=
`probe_interpret_latency` 延迟 + 术语命中率。附带搬 akang 的**读音提示字段**
（term/pronunciation/replacement 三元组）进术语表 schema。

**E6（P3 新增）词条沉淀闭环门槛**（type4me 参数直接可抄）：≥3 独立会话、跨 ≥2 自然日、
同向占比 >80%、无等强冲突、每条记录最多贡献一次、90 天半衰期；状态机
pending/accepted/ignored/conflicted/stale；**批量建议永不自动写全局词表**——
与 L-① adopt 的人工确认原则一致，补上统计学门槛。

### 25.4 对「最终要准确知道用户要表达什么」的校准（用户论点）

五方一致：

- **逐字还原**：已被我们的 V-3.3/V-7/V-3.2 与 VoxType 作者结论（标点模型改不了 ASR
  错字）、type4me 的 Guard-回退设计共同否决。信息销毁处无解。
- **意图级准确**的可行链条（投资顺序）：语言钉定 hint（已上线）→ 热词（边际已尽，
  停止加码）→ **E1 snippet 词级修正（新，主力补位）** → QA 词条字面覆盖（L-① 挖掘，
  E6 门槛）→ margin 低置信澄清（§23.5 已定规格）→ 垫话兜底。意图识别选对 QA/垫音，
  受上游文本质量支配——所以钱花在出稿质量与词条覆盖上，判定层按 §23.5 已定稿的

### 25.5 不搬清单（明确记录，防后人重查）

### 25.6 更正与模式映射（用户指正后修订）

**上一节表述有一处不严谨**：type4me 并非「LLM 默认关」——那是 VoxType 的取舍
（LLM 校正默认关、可开）。type4me 的 8 个模式里只有**快速模式**零 LLM；
智能感知/翻译/随便问/润色/Prompt 优化/任务委派都以 LLM 为主引擎，智能感知是默认
主力。两者共同遵守的是三条纪律，而非「关 LLM」：①只在终稿后**单次**调用
（不对 partial 打 LLM）；②OutputGuard 拒绝即**回退原文**；③词汇知识活在 LLM 之外
（热词+snippet，prompt 保持纯净）。

模式逐个映射到我们两条线：

| type4me 模式 | 我们的对应物 / 落点 | 结论 |
|---|---|---|
| 快速模式（零 LLM） | A 线 QA 快路、直念步（say=1）、垫话、心跳——零 LLM 出声轨道**已存在且同构** | 已有 |
| 智能感知（LLM+上下文+Guard） | A 线回复生成（system 前缀=语言规则+对象档案+话术总览+步尾部 ≈ 它的冻结上下文快照；人设 tone ≈ 它的场景策略枚举）；**缺它的是 OutputGuard 纪律** | E3 即我们版 Guard |
| 语音润色（确定性精炼） | **我们没有，也不进实时轮**——多一跳 LLM ≈ +200-600ms，A 线轮预算紧；正确落点=**异步面**：挂断后纪要清洗、QA 挖掘（mine_qa_pairs）与 L-① 漏网轮的输入预处理 | **新增 E7** |
| 翻译（校验+单次重试） | B 线 MT 已同构（术语槽/语气标记/引号剥离）；它的「语言校验器+单次重试」我们没有 | **E5 增补** |
| 随便问/Prompt 优化/任务委派/Mac 操作 | 客服域无对应（坐席不问 AI、不产 prompt、不操作桌面） | 不搬 |

**E7（P3 新增）离线润色面**：Voice Polish 式确定性精炼（删口水词/重复/半句废弃、
改口取后值、口语数字规范化），带 OutputGuard（保数字/否定/语言），跑在**挂断后**的
纪要生成与词条挖掘输入上——延迟不敏感，直接提升学习闭环的输入质量（脏转写是
qa_cluster 簇不纯的主因之一）。验收：对 R1 真实集 152 条跑 dry 挖掘，对比簇纯度；
纪要质量人工抽检。

**E5 增补**：B 线 MT 出口加确定性语言校验 + 单次重试（type4me Translation validator
形态：错语言置信阈值 + 强化重试 prompt，重试仍败按现状出稿不回退原文）。

## 26. 源码级移植规格（2026-09-21 三路下钻：读实现不读宣传）

三路并行代理把四仓核心源码读到函数级。先列三个**照 README 抄必然抄错**的事实，
再给 E1-E7 逐条的移植规格与参数速查。

### 26.1 三个「抄对」级别的关键发现

1. **type4me 的内置词表根本不生效（最大陷阱）**：`SnippetStorage.apply` 只编译
   用户 `snippets.json`，`builtin-snippets.json` 那 100+ 条映射**从不进入替换路径**
   （只在去重比对和 Finder 展示时被读）；`HotwordStorage.loadEffective()` 也只返回
   用户文件，无 builtin 合并、无去重（头部注释声称的 "merged, deduplicated,
   case-insensitive" 与实现不符）。→ 我们做 E1/E2 时**词表必须单点合并生效**
   （内置行业词＋运营模板词＋挖掘词条 → 一份 effective），别抄它的存储分层却漏了
   生效路径；我们现行的 `asr_hotword_context` 三层合并恰好是对的，snippet 轨照此办理。
2. **VoxType 的「保守校正契约」是 roadmap 不是代码**：`llm_refine.h`（header-only，
   无 .cpp）全文没有 JSON schema、没有 change ratio 上限、没有数字/URL/代码保护正则
   ——那些只写在 roadmap 里。实际契约=纯文本输出＋`temperature 0.1`＋`max_tokens 1024`
   ＋失败/空回退原文（唯一回退点一行：`res.success && !empty ? text : asrText`）。
   → E3 的参考实现**只认 type4me 的 `IntelliSenseOutputValidator`**，VoxType 仅佐证
   「失败回退原文」这一条纪律。
3. **akang 的 `[EMPTY]` 哨兵只有 Windows 端强制**（`VoiceInputPrompt.IsUsable`：trim
   后空或与 `[EMPTY]` 全等→不可用）；macOS 端无 `IsUsable`，哨兵纯靠模型自觉。
   → 我们抄要抄 Windows 形态：**引擎侧硬判定**（等价物=我们的犹豫残片门/静音守卫，
   已有，验证了方向）。

### 26.2 E1-E7 移植规格（源文件/函数 → 抄什么/改什么/别抄什么）

**E1 snippet 后置正则轨**（源：`SnippetStorage.swift`）
- 抄：`buildFlexPattern`——trigger 去全部空白→逐字符 `re.escape`→`\s*` 连接→前后
  `(?<![a-zA-Z0-9])…(?![a-zA-Z0-9])`（ASCII lookaround，不用 `\b`——CJK 边界 `\b`
  失效）；`re.IGNORECASE`；替换值用回调形式防 `$`/`\` 展开；规则**串行链式**（前条
  输出=后条输入）；JSON `[{"trigger","replacement"}]` 原子写。
- 改：**加非空 trigger 守卫**（它没有——空 trigger 会生成匹配空串的正则，逐位置插入
  替换值，破坏性）；per-App 覆盖用 pattern 字符串精确相等是坑（大小写不同的 trigger
  不互相覆盖、两条都跑），我们单租户单层词表不需要这层，直接一份 effective。
- 生效点：ASR FINAL 之后、意图判定/QA 匹配之前（我们侧=agent 收到 final 转写处）。

**E2 热词准入与泄漏清洗**（源：`Qwen3HotwordLeakSanitizer.swift`＋`server.py`）
- 清洗器完整算法：分隔符集=空白∪`,，、;；:：|/\-—_·.。.!！?？"'""''()（）[]【】<>《》`；
  标签表=`Vocabulary:/Hotwords:/词汇：/词汇表：/热词：/关键词：`（带全角冒号变体）；
  **最长连续热词前缀**=从串首起按词表顺序连续匹配（词间可跳分隔符，锚定+大小写不
  敏感，断了即停），得分先比词数再比消费长度；泄漏判据=有标签**或** ≥2 连续热词；
  单词泄漏需 fallback 与 consumed/remainder 满足前缀/后缀关系且 consumed 含 CJK
  (4E00-9FFF)；命中→剥前缀取 remainder（与 fallback 归一化后相等/互后缀则保
  remainder，否则用 fallback）。归一化=lowercase+去分隔符。
- 两个已知边界（照抄前要决策）：纯热词 dump（remainder 空）**不清洗原样保留**（它的
  测试锁定的行为，我们建议改为整段丢弃→走静音分支）；它有一条调用路径没传
  fallback（单词泄漏漏网），我们实现时 fallback 必传（上一次 partial/前置句）。
- server.py 侧佐证我们现状：`context=` 空格 join **不加标签**（加标签会回声）＋
  0.3s 最短音频＋RMS<1e-4 静音守卫——与我们 sidecar/VAD 门控同族，不必改。

**E3 OutputGuard 确定性后验**（源：`IntelliSenseOutputValidator.swift`＋
`CorrectionIntentAnalysis.swift` 内联的 `ProtectedFactExtractor`）
- 硬保护 token 正则（逐字可移植）：URL `https?://[^\s<>]+`；邮箱
  `(?i)[A-Z0-9._%+-]+@[A-Z0-9.-]+\.[A-Z]{2,}`；字面路径 `(?:/[^\s/]+){2,}`；数字
  串 `(?<![A-Za-z0-9])\d+(?:[.,:/-]\d+)*(?![A-Za-z0-9])`；星期
  `(?:周|星期|礼拜)[一二三四五六日天]`。软保护：`--flag` 类与 camelCase/下划线
  标识符（只告警不拒）。
- 硬拒绝判定序与阈值：空输出→```围栏→tool_call 标记→回应标记被改→「答案是/好的/
  以下是…」抢答前缀→「已为你/操作完成」执行声明（需输入含请求信号）→**硬保护
  token 丢失**（整 token 完全匹配才算硬）→**prohibition/never 两类否定计数不等**
  （其余四类只告警）→扩张上限 `max(3N, N+120)`→语言漂移（输入 CJK≥4 且输出 CJK=0；
  或双侧 total≥8 且 CJK 占比 0.65/0.2 交叉；只数 4E00-9FFF+ASCII 字母）→敏感新增
  （三条正则：`api[_-]?key|secret|access[_-]?token|password` 赋值形、`Bearer` ≥12
  字符、`-----BEGIN PRIVATE KEY-----`；**只在输入没有输出新增时拒**）→编造事实
  （新增 token 含数字且非行首列表标记，且输入本有保护 token）。
- **reject→finalText=原文**（candidate 永远留档可审计）。挂点：QA 快路匹配前 +
  意图判定结果后 + E7 离线润色出口。

**E4 改口检测**（源：`CorrectionIntentAnalysis.analyze`）
- 两条正则：显式标记 `不对|哦不|改口|算了|重说|i mean|sorry`（可选后缀
  `[，,。.]?(改成|换成|应该是|是)`）＋独立后续词 `改成|换成|应该是`（`(?!不要)`）；
  均带 `(?<!不)(?<!别)` 负向后行，命中后再查**区间前 4 字符**是否以 不要/不能/别
  结尾，是则丢弃。
- 记账：区间后第一个保护 token→required；区间前最后一个与之不同（大小写不敏感）
  →superseded 并移出 required。
- **「不是A是B」豁免的实现=词表里根本没有「不是」**（不是显式分支）；否定计数=
  先删元话语（不对/哦不/i mean/sorry；能不能/是不是/要不要/是否；不过/不仅/不管）
  再六分类顺序消费（prohibition→inability→absence→contradiction→never→general），
  每类计完替换为空格防重复计数。
- 落点：`FlowController` 的 CONFIRM/UNCLEAR 判定与 WA 累积轮；**注意 Voice Polish
  模板把「不是」当改口、IntelliSense 不当**——两模板语义相反，我们话术域取
  IntelliSense 口径（豁免），离线润色面取 Polish 口径（取后值）。

**E5 B 线 MT 校验+重试**（源：`TranslationOutputValidator/TranslationPromptBuilder`）
- 三阈值：自然语言字符（只数 letters 标量）**<12→告警**；目标语置信 **>0.03 即
  accept**；dominant 错语置信 **≥0.90 且目标 ≤0.03→unexpectedLanguage**。校验前先
  清理七类噪声（围栏/行内码/URL/邮箱/路径/点分标识符/数字串→替换空格）。
- Policy：unexpectedLanguage 首次→retry（`IMPORTANT RETRY:` 前缀+完整原 prompt），
  retry 再错→reject；empty/unsafeStructure（`<tool_call>` 等）立即 reject 不重试；
  lowConfidence/insufficient 恒 accept。15s 重试超时。
- 与我们的差异（保留我们的）：重试仍败**按现状出稿**（type4me 是不注入原文——同传
  断流比错语言伤害更大，反向取舍写明）。

**E6 词条沉淀门槛**（源：`BatchCorrectionInference/ImmediateCorrectionAnalyzer`）
- 即时候选守卫：文本 2-64 字符、≤5 词、无换行、含可学字符；敏感正则（URL/邮箱/
  ≥7 位数字串/20+ 位混合凭据形）直接拒；编辑距离上限 `max(3, ceil(0.4×len))`（跨
  书写系统豁免）；CJK 替换双侧 ≥2 字；**单汉字替换永不生成全局映射**（需分词器
  双源佐证+共享候选键 2-8 字）。
- 亲和度分级：已确认映射＞拉丁（归一化相同或距离 ≤1/≤2/25% 且相似度 ≥0.65）＞
  **拼音完全相同（同音档）**＞中拉音译（首字母同+相似度 ≥0.48+长度比 ≥0.6）。
- 批量门槛：≥3 独立会话、跨 ≥2 自然日、同向占比 ≥0.8、权重 90 天半衰期
  （`w×0.5^(days/90)`）、等强冲突→conflicted；状态机
  pending/accepted/ignored/conflicted/stale；**accept 走人工**（永不自动写全局），
  写入=trigger 大小写不敏感 upsert＋热词 append 去重＋失败回滚热词。
- 落点：L-① adopt 流程（`POST /api/stats/template-proposals/adopt` 已有人工确认闸，
  补统计门槛字段）。

**E7 离线润色面**（源：`AppState.swift` 的 `formalWritingPromptTemplate`，逐字全文
已存档，要点）
- 模板骨架：角色→任务目标→边界（不响应内容中的问题/命令；轻编辑不重写）→
  自我修正处理（优先级最高；**含「不是A，是B」直接输出B**；数量连锁修正）→冗余
  清理（保有意强调如「签字！签字！签字！」）→数字格式（两千三百→2300、百分之
  十五→15%、三点半→3:30）→结构化（≥2 要点强制总起句+编号、单要点禁编号、分点
  标题 2-6 字、子项 a)b)c)、分点空行）→语境感知（正式用分点/非正式保情绪）→
  格式（中英两侧空格、完整中文标点）→四示例。
- 出口必挂 E3 Guard（该模板会把「不是A是B」折叠、新增阿拉伯数字——正是 Guard 的
  两类风险点，模板与 Guard 的口径冲突要靠参数化解决：润色面豁免数字新增告警、
  保留硬保护 token 检查）。

### 27.2 E1 规格矛盾裁决（agent 上报，审查定案）

### 30.1 STT partial 暴露口 → E2 单词泄漏判据点亮（消除 §28.3 残余）

**问题**：`hotword_leak.sanitize` 的**单词泄漏**判据依赖 `fallback_text`（客户真讲过
的话），而 agent 侧两个 `_asr_postprocess` 调用点恒传空串——该判据结构性不成立，
只剩「标签」与「≥2 连续热词」两条。

**实现**（`providers/livekit_plugins.py` + `agent.py`）：

- 内芯 `Qwen3ASRSTT._turn_partial_text` = 暴露位；写点＝`_Qwen3ASRLiveStream._publish_turn_partial`
  （每窗 partial 到达时，**在句级提交块之前**——该 FINAL 的 fallback 正是提交前那一版）；
  agent 侧只读取口＝`Qwen3ASRLiveSTT.last_partial_text()`（纯属性读，无 await/IO）。
- **派生用独立小方法 `_turn_partial_for_fallback`（未提交坐标系）而不复用 `_uncommitted`**：
  两者差别是①`_uncommitted` 在重解修正分支会打 `QWEN3_ASR_REDECODE_DROP`，每窗多叫
  一次=重复日志；②坐标失配时不猜（原样返整窗，给长了判据自然不成立）。
- **清零语义（关键设计，与「在 FINAL 处清零」的直读不同）**：`_reset()` 清、`_start_session()`
  清（新语音段=新一轮），而两条 FINAL 发出点（停嘴 EOS / join-flush）在 `_reset()` **之前**
  取 pre-reset 快照、**之后**按「确实发出了 FINAL」重贴回来。理由：`_run` 里的次序是
  `payload → _reset() → send FINAL`，而 agent 钩子在 FINAL **之后**才跑——若「提交即清」，
  停嘴路径的 fallback 将**恒为空**。第三个 `_reset()` 调用点（F4 收线/告别直念窗整段放弃）
  不重贴是对的：该段本就整段丢弃、无 FINAL。
- 流收官**不**清（在途钩子还要读）；跨轮残留由「内芯每通一个」+ 新一轮 START 清零兜住。
- 接线：两个调用点都传 `fallback_text=_last_partial_text(_partial_gate_stt)`；取口整条
  fail-soft（缺方法/None/抛异常→空串，非 live 包装与假 STT 天然空串）。

### 31.1 CP 启动锚：非回环 bind × 认证双关 = 拒绝启动（§30.4 ①，落地）

- 判据（纯函数 `_unsafe_open_bind`）：`BOK_AUTH_REQUIRED` 与 `BOK_CP_TOKEN` **皆空** 且 bind
  非回环 → `_startup()` 抛 `RuntimeError` 拒绝启动，且**排在 DB 迁移/种子之前**（配置事故零副作用）。
- bind 解析两源（`_resolved_bind_host`）：**argv `--host`**（uvicorn 实际吃的值——Dockerfile /
  deploy CMD 显式 `0.0.0.0`）优先，其次 `BOK_BIND_HOST`（`tools/bok.py::_cp_bind_host` 唯一来源），

  env 缺省原为 `"*"`，把「显式配置」与「缺省」混同，令裸放行档的收窄永不生效（env 缺省改 `""`）。

  随机生成**——写死的 `*-0123456789*` 形状会命中 gitleaks 的 `generic-api-key`（`.gitleaks.toml`

### 34.1 CI 随机 SIGSEGV：**先复现、再动**（机制级，不等运气）

§32.4 记的「既有缺陷、本机复现不出、留待复现窗口」在本批次拿到了窗口，但走的是
**机制级复现**而非等全量套件的随机崩：

1. **焦点窗口复现不出来**（与 §32.4 一致）：8 个 StaticPool 文件连跑 **200 轮 → 0 崩**。
   故「改完再跑几轮看看还崩不崩」这种验证**结构性无效**——基线本来就是 0。
2. **转机制级**：复刻该形状（内存库 + StaticPool）+ 4 线程持续读 + 300 次 `dispose()`：

   | 形状 | 结果 |
   |---|---|
   | `sqlite://` + **StaticPool**（现状） | **SIGSEGV rc=139，3/3 全崩** |
   | `sqlite://` + NullPool（对照） | rc=1 `no such table`——每次检出各得**一个空内存库** |
   | **文件库 + 默认 QueuePool**（拟改） | **存活 300 次 dispose，worker 错误 0，2/2** |

   第二行是**关键旁证**：内存库要「跨线程同一个库」**只能**靠共享同一条连接（NullPool
   连表都看不见），所以病灶不是「选错了池」，而是「内存库 + 跨线程」这个组合本身。
3. **修法**：8 处引擎点（5 个 `sql_repo` yield 夹具 + 3 个函数内联；每文件恰好 1 处）
   一律改 `tmp_path` 文件库 + 默认池；`check_same_thread=False` 保留（TestClient 请求
   跑在 anyio 工作线程），另加 `timeout=30` 兜写锁竞争。夹具 docstring 与那两处
   「照 X 姿势」的注释改写为**记录病灶本身**（原先的注释只教人复制，正是它把形状传了 8 份）。
4. **新门禁** `tests/test_sqlite_fixture_pool.py`：禁 `poolclass=StaticPool` 在 `tests/`

   139，会连整个 pytest 会话一起带走，拿不到用例级报告、CI 上还容易被当环境抖动重跑掉。
5. **验证**：全量套件 **连跑 12 轮，12/12 全绿**（每轮 2427 passed）。口径说明：CI 基线

### 36.1 抓到的缺陷：「静默空音频」——探针全哑的真凶（不是 agent 回归）

**症状**：`e2e_barge_in` / `probe_filler_timing` / `e2e_real_customer` 第一批全部失败。
最刺眼的一通（call-32451e12）：开场白正常播出（`greeting_playout_done +5526ms`，
`AGENT_METRICS tts ttfb=843ms audio=4.37s`），之后**3 分钟零日志**、账本里**只有 1 条
（开场白）**、客户 6 轮一条没进——表象完全像「agent 听不到客户」。

**排查链**（每步都排除了一个假设）：
1. 不是 agent 订阅问题——agent 侧连 STT 会话都没建，但也**没有任何报错**；
2. ASR sidecar 在收 chunk（`/api/chunk` 200），但那些会话**对不上这通的时间**；
3. 决定性读数来自探针自己：每轮都印 `话音0.0s`——**它推给房间的客户音频是空的**；
4. 直打 `:8788/v1/audio/speech`（探针同 payload）→ **HTTP 200 + 0 字节**；
5. `tts.log` 里才有真相：
   `FileNotFoundError('Config not found at /Users/halo/.lmstudio/models/mlx-community/Qwen3-TTS-12Hz-1.7B-CustomVoice-8bit')`。

**根因（两个缺陷叠加，缺一个都不会这么难查）**：
- **空壳遮蔽**：`~/.lmstudio/models/mlx-community/Qwen3-TTS-12Hz-1.7B-{CustomVoice,Base}-8bit`
  是**只有 `.cache/` 的空壳**（2026-09-21 11:37 被别家工具建），真模型在 app-data；
  而 `bok.model_path` 的判据是 `dir.exists()`，**先查 lmstudio 且空壳即命中** → 返回空壳。
  （`serve` 自检反而报 `[ok] tts_preset present`——因为 `_model_present` 先看 app-data。）
- **静默失败**：sidecar 的 `ensure_loaded()` 只在**生成器内部**调用，那时响应头已发、
  状态码已定 200，抛出的 503 改不了状态 → 客户端拿到「成功但没声音」。**静默失败比报错贵**。

**修法（两处，各配判例）**：
1. `tools/bok.py` 新增 `_usable_model_dir`（**要 `config.json`**，不是「存在」也不是「非空」），
   `model_path` 两个布局都用它；优先级与「两边都没有」的兜底行为保持不变。
   复核：真模型表 6 项全部解析到可加载目录；其余 7 个模型（ASR/VAD/4B/9B/2B/MT）判据未受影响
   （逐个核过 `config.json`）。
2. `services/qwen3-tts-sidecar`：`ensure_loaded()` 提前到**返回 StreamingResponse 之前**
   （fail-fast 503）。

- 切换装置本身（批次 4，§30.2）就按「**刻意的、显式的**」设计：`resolve_stimulus_backend`

| ASR 解码在跑 | 1009ms | +156ms |

外加：**9B 跑一次判据形状请求要 4537ms**——一次开火占 GPU 4.5s，横跨 2-3 轮。**主嫌=9B judge，ASR 只是小数。**

**方法论坑两条（值得记）**：第一版探针得出「没有争用」的假结论，原因有二——(a) 负载线程 `Thread(target=load)` 漏传 `args`，负载根本没起；(b) 修好后仍假，因为**同一份 prompt 重复请求全走前缀缓存**（同一判据 prompt 从 4878ms 掉到 301ms），量到的是「cache hit + 1 token」。修法是每次请求换 nonce（`_fresh`）——真实链路每轮都是新 token。

### 38.4 错峰闸：实测够不着空闲窗 → **默认关**

按「judge 判定下一轮才消费，晚几秒零损失」的思路实现 `_wait_link_idle`（floor=旧 `FLOW_JUDGE_DELAY`，再等链路真空闲：AI 在听 + 客户没在讲，硬上限 `FLOW_JUDGE_IDLE_CAP`），接在两个 judge 的开火前。

**真栈 soak 实测（call-fc12493c，11 轮/0 哑 PASS）：9 次开火全部 `capped`——一次没等到空闲。**
原因：soak 的回复时长 10-19s，普遍超过上限；闸只把开火从 3s 推到 8s，**没避开 prefill 窗**。
故**默认 `FLOW_JUDGE_IDLE_CAP=0`（=逐字节同旧的固定让路）**，闸留作可开档（开之前先做 A/B，观测面=`[judge] yield capped` 占比 + 既有 `judge_pending_expired`）。
判例 `tests/test_judge_idle_yield.py`（5 条：空闲即走/忙则等到空闲/客户讲话也算忙/到点必须放弃/**cap=0 必须保持旧语义**）。

单次对照（改前云基线 so/改后）首声 p50 2576→1721、p95 6407→4051、perceived p50 3893→2527——**n=1/臂，不归因**（闸全 capped，改善更可能来自「开火从 3s 推到 8s」的位移与跑次方差）。

### 38.5 结论与下一步（按性价比）

1. **judge 挪出本地 GPU** 才是长回复轮的正解：判定是后台文本任务，走云端（DeepSeek 路径已在）＝零本地 GPU 占用，还能顺带省掉 9B 常驻显存。比「延时错峰」干净。
2. **压 judge 自身 prefill**（判据集+转写 4.5s）：裁判据集或换更短判据格式，收益直接。
3. **记忆旋钮（零代码）**：`REPLY_MEMORY_LINES` 6→3-4 直接砍 ~280-380 tok（≈0.45-0.6s/轮）；每行 ≤200 字改要点式是代码档。改动后验收＝本工具前后差 + 300 轮 TTFT 回归。
4. 兜底推迟（抬 3s 死线）**不做**——只是把痛苦推后，用户已拍板。
