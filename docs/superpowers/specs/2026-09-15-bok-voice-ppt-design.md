## 2. 全篇硬约束

1. **零第三方品牌名，且「开源」字样不出现**：不出现任何被引用的开源项目/供应商名（LiveKit、MiniMax、Qwen、Tauri 等），正文连「开源/开源技术栈」这类措辞也不用。只讲能力，不讲技术栈。硬件平台名（NVIDIA/CUDA、Apple Silicon）允许出现。
2. **「垫话/垫音」词汇禁区**：只描述听感（生成间隙自然应承、无冷场），绝不提内部机制名。
3. **成本口径诚实**：不承诺「无按量 API 费」。真实结构=三层（见 P16）。
4. **对外脱敏**：不出现通话 ID、内部工具名、真实客户数据；实证案例只讲故事弧线。
5. **占位标注**：业务数据缺口统一 `[占位：待补]`，工程指标可直接引用仓库实测值。
6. **「无审查版」措辞对外分寸**：正文用「模型完全自托管 · 无云端内容审查干预 · 话术执行稳定可预期」；「无审查版」字眼视听众可加深。

## 4. 逐页大纲（22 页）

### 封面

- **P1 封面**：Bok Voice — 全自动实时语音 AI 客服 · 本地部署 · 三语 | 同传工作台。版本/日期脚注。

### 第一幕 · 为什么是现在（P2-P4）

- **P2 行业结构性痛点**：人力成本与流动、培训周期长、话术执行不标准、录音与客户数据合规压力。客户共鸣 + 市场规模入口。
- **P3 现有方案两难**：云端语音 AI=全链路按量计费+数据出域+黑盒不可控 ↔ 纯人力=贵、不可扩展。中间地带是空的 → 引出本地智能。
- **P4 为什么是现在**：三个拐点（去品牌化）：语音技术栈成熟 / 消费级高性能芯片算力到位 / 端侧自托管方案工程化可行。

### 第二幕 · 我们已经建成什么（P5-P16）

- **P5 产品全景**：双产品线（A 线客服 / B 线同传）+ 六域能力全景图（实时对话引擎 / 话术可控 / 运营管理 / 部署形态 / 同传 / 安全合规，各一格一句）。
- **P6 全自动生命周期**：名单导入 → **批量 SIP 自动外呼** → AI 三语对话 → **WhatsApp/微信号码自动捕获记录** → 挂断自动结算 → 自动沉淀 → 自动下一通。「全自动」贯穿。
- **P7 像真人一样对话**：每通固定语言（普/粤/英）、真打断让位+误打断自愈、句级实时响应。
- **P8 声音像真人 · 试听**：三语音色库 + 声音克隆。**PPT 内嵌短音频、点击即听**（制作时验证内嵌方案，兜底：随包附带音频文件+页内标注）。
- **P9 反应像真人**：常用问题张口即答（沉淀的常用语库）· 生成间隙自然应承衔接（听感无冷场）· 常规对话暖轮可感知延迟 ~1s 档。
- **P10 越用越聪明（自适应学习闭环，四层）**：①高频问答自动沉淀（真实通话挖掘，毫秒级应答）②领域词表自适应（按话术与对象自动学习专有名词，越听越准）③对象记忆延续（每通沉淀客户档案，下次开场即续聊）④话术运营闭环（话术/快答库随业务分层进化）。副产品：高频内容缓存复用=越用越便宜。
- **P11 话术不脱轨**：分步话术引擎、合规内容零延迟照读、号码捕获闭环、防复读机制。
- **P12 管理全程可控**：管理员**实时监听 / 一键掐断暂停 / 全程记录留痕**；外呼战役+名册；三层角色权限+按人授权；全程审计。
- **P13 同传工作台（上）**：双向同声传译、双栏实时字幕、输出设备路由——一机两用。
- **P14 同传工作台（下）**：场景价值（跨语言商务会谈/跨境客服/培训演练）——第二场景已跑通=平台化愿景的早期证据。
- **P15 部署形态与硬件门槛**：桌面 → SIP 电话边缘 → 分布式节点 → 云端/机房，一条演进路径。硬件六档容量故事（每档=显卡+CPU+内存+硬盘+**并发量**五要素，内部全表见 §7.5，PPT 只出档位+并发量）：单通体验=单卡 5090（1-2 路）→ 生产最低=双卡 5090（10-20 路）→ **入门一体=双 DGX Spark（≤20-25 路+夜间 1M 优，~¥8 万）**→ 生产推荐=2× PRO 6000 Max-Q（25-30 路）→ **企业级 50 并发=4 卡 PRO 6000 起步（白天 50 路语音+夜间知识库长文分析，时间分离一套硬件两用）**→ 云端/机房（8 卡 H200，100-150 路级）。整机配置单见 §7。
- **P16 本地优先四重价值**：①隐私（数据不出域）②成本（三层结构：理解思考零 API 费、仅语音合成按量、高频缓存摊薄）③稳定（完全自托管模型——话术不被云端审查误拦、不受第三方策略漂移影响）④可控（全链路可审计可定制）。

## 6. 附录 · 27B 级模型「保证 100+ tok/s」硬件调研（2026-09-15 二轮深查；内部依据，PPT 只出档位结论）

Qwen3.8-27B（dense）显存：FP16 ~54GB / Q8 ~28GB / NVFP4·Q4 ~15-17GB。**单流解码是内存带宽瓶颈，不是容量瓶颈。**

### 6.1 各档实测（Qwen3.8-27B 或同级 27B，单流解码）

| 配置 | 显存/带宽 | 实测 tok/s | 判定 |
|---|---|---|---|
| 单卡 RTX 5090 | 32GB / 1.79TB/s | Q4_K_M 短会话 65.7；NVFP4@262K 上下文 77.2（128K 驻留回落 64.7）；Unsloth GGUF 峰值 ~108 | 峰值过百但跨上下文/并发不构成「保证」；32GB 装 Q8 质量档后无 KV+ASR/TTS 余量 |
| **双卡 RTX 5090（TP=2）** | 64GB / 2×1.79TB/s | 65-80 基准（社区共识≈单 H100：HN 实测 80 vs H100 78）；叠量化+投机解码 100-160 | **「保证 100+」的最低配**：Q8 质量档 + 长上下文 KV + 同机 ASR/TTS + 多路并发余量 |
| 2× RTX PRO 6000 Blackwell Max-Q | 192GB / 2×1.79TB/s | 同带宽量级，显存×3 | **推荐配**：FP8 质量档 + 巨量 KV + 3-6 路通话并发；300W 涡轮单风扇双槽可堆叠，整机功耗/噪声友好 |
| A100 80GB | 80GB / 2TB/s | 单流 ~40-60 | 数据中心形态，归云端线 |
| DGX Spark 单机（GB10） | 128GB 统一内存 / ~273GB/s | FP16 ~4.5（TTFT 43s）；FP8 ~10；NVFP4+MTP 34-47 | 带宽墙，实时语音不合格 |
| DGX Spark 双机串联 | 2×128GB / 2×273GB | MoE（GPT-OSS-120B mxfp4）：单机 57.5 → TP2 集群 69.0（**仅 1.2×**）；dense 理论 ~2×（带宽分片）但无 27B 硬数据，27B 上限估 60-90（NVFP4+MTP） | **技术上可行**（QSFP 直连 ConnectX-7，vLLM TP2+Ray），但绝对速度不达标；真实价值=跑 122B/397B 大 MoE、大上下文、多服务常驻 |

### 6.2 关键机制注记

- **MTP/投机解码不是免费午餐**：接受率 80.4% 时每步赚 ~1.8 token 但单步开销 ~4×；HF 讨论实证长上下文下关 MTP 反而 19.9→72.3 tok/s。语音场景上下文中等（数 K token 级）受影响小，但「保证 100+」要靠双卡带宽余量兜底而非单叠 MTP。
- 5090 无 NVLink，双卡张量并行走 PCIe 5.0 P2P（TRX50/WRX90 双 x16 平台），vLLM/SGLang 一条 flag 即开。
- 双 5090 共识：约 10% 价格拿到 H100 的 ~83% 体验（r/LocalLLaMA 实测帖）。

### 6.3 企业私有化 50 并发 + 1M 上下文（2026-09-16 增补；核心约束=KV cache 显存总量，不是带宽）

**KV cache 数学**（27B dense，64 层 GQA）：FP16 KV ≈128KB/token → **单个 1M 上下文会话 ≈128GB KV**（FP8 KV 64GB / 4bit KV 32GB）。vLLM KV 量化实测可省 ~74%。

**两种需求读法与对应配置：**

| 读法 | 负载画像 | 需求测算 | 配置结论 |
|---|---|---|---|
| A（产品现实·推荐架构） | 50 并发**语音**会话（每会话活动上下文 8-32K）+ 1M 长上下文能力用于**知识库摄入/历史蒸馏/审计分析**等少数重任务 | 语音 KV：50×32K×128KB≈200GB FP16→FP8 ~100GB，叠加共享话术前缀缓存（所有通话共享一份）实际更低；聚合解码 50×40-60 tok/s≈2-3K tok/s ≪ 4×H100 实测 22K tok/s（10× 余量）；1M 单会话 FP8 KV 64GB 单卡 H200/B200 可装 | **1-2× HGX 8×H200（1.13TB）/8×B200（1.5TB）**：6-7 卡 LLM（TP/PP+大 KV 池）+ 1-2 卡 ASR 50 路流式；1M 任务走 KV 分层卸载（LMCache/Mooncake→CPU RAM/NVMe，Mooncake 长上下文吞吐 +525%） |
| B（极端：50 会话×1M 同时驻留） | 每会话背 1M 活动上下文 | KV 总量 50×64GB（FP8）≈**3.2TB**（FP16 6.4TB）＞任何 8 卡单机（8×B200=1.5TB） | GB200 NVL72（13.5TB 单 NVLink 域，官方定位即 1M 上下文推理）单机可扛；或 2-4 台 HGX B200 多节点 + Mooncake/LMCache 分布式 KV。**产品架构上不建议**：语音会话该用共享前缀+检索+滚动窗口，1M 是知识库/分析任务属性——Kimi/Mooncake 的设计动机同源 |

**50 并发语音的 LLM 之外配套**（部署规划必算）：ASR 50 路流式 ≈1-2 张专用 GPU；TTS 云端并发配额需商务锁定；LiveKit SFU/控制面/DB 走 CPU 服务器；内网万兆（50×~100kbps 音频流宽裕）。

**吞吐参照**：Qwen 3.5 27B on 4×H100 vLLM 实测聚合输出 ~22K tok/s；96×B200（GKE）达 1M tok/s 级总吞吐——50 并发对吞吐是轻负载，**瓶颈全在 KV 显存与 TTFT SLO**。

### 6.4 262K 上下文 + 50 并发·按实际任务画像定配置（2026-09-16 二轮；产品口径以此为准，1M 为扩展档）

**KV 实测口径修正**：27B GQA 实测 KV ≈**64KB/token**（wal.sh Qwen3.6-27B 实测；HF 实证单张 96GB PRO 6000 以 BF16 权重 54GB + 完整 262K 上下文（~16GB KV）同卡运行 @78 tok/s）→ **262K 会话 KV：FP16 ~16GB / FP8 ~8GB**。

**实际任务画像**（A 线语音 + 知识任务分层）：

| 任务 | 上下文特征 | KV 需求 | 吞吐需求 |
|---|---|---|---|
| 语音会话 ×50 并发 | 共享话术/系统前缀（全通话共享一份，前缀缓存）+ 每会话活动上下文 8-32K + 每轮新增 ~300 tok | 50×32K×64KB≈100GB FP16 / 50GB FP8 + 1 份共享前缀 | 聚合解码 50×40-60 tok/s ≈2-3K tok/s；prefill 每轮仅尾部 |
| 262K 长文任务（知识库摄入/审计分析/历史蒸馏） | 批处理任务，并发 1-4 足够 | 单任务 8-16GB KV | prefill 262K：单卡 5090 级 166s / H200 级 ~15-25s |
| 知识助手型 50 用户×262K | 262K 主体是**共享知识库前缀**（同文档集） | 前缀缓存坍缩：1 份 262K 共享 KV + 50 个小尾巴 | prefill 风暴被前缀缓存吸收 |
| 极端 50×262K 全独立上下文 | 每会话 262K 互不相同 | 800GB FP16 / 400GB FP8 | 8×H200 单机可装（FP8 从容/FP16 紧） |

**配置方案（262K 口径）**：

| 档 | 配置 | 承载 | 说明 |
|---|---|---|---|
| 部门级性价比 | **2 节点×4 卡 RTX PRO 6000 Max-Q（8 卡 768GB）** | 语音池 4-5 卡（continuous batching，~120 t/s/GPU 档）+ 262K 批任务 2 卡（每卡 1-3 个 262K 会话，SGLang+EAGLE 实测单卡 78 tok/s@BF16）+ ASR 1 卡 + 备用 1 卡 | GPU 预算 ~¥50-90 万（MSRP vs 街价）；注意 vLLM Blackwell SM120 镜像成熟度，SGLang 为备选 |
| 企业标准 | **1× HGX 8×H200（1.13TB）**，N+1 可选双机 | 语音 4-5 卡（DP 副本×12 流/卡）+ 262K 批任务 1-2 卡（141GB/卡：FP8 权重 27GB+3-8 个 262K FP8 KV）+ ASR 1 卡 + 冗余 | 整机 ~$25-40 万 |
| 极端独立 262K×50 | 8×B200（1.5TB）或 2×8×H200 | FP8 KV 400GB 装入单机 8×B200 | 或走 KV 分层卸载省一半 |

**与 1M 档的关系**：1M=262K 的 KV×4（单会话 64GB FP16/32GB FP8）——架构不变、容量档位上移一档（8×B200 起步或 KV 卸载），见 §6.3。

**关键实测锚点**：单卡 5090 NVFP4@262K 解码 77.2 tok/s（128K 驻留 64.7）；单卡 PRO 6000 BF16@262K 78 tok/s（SGLang+EAGLE）；PRO 6000 每 GPU ~120 t/s、每服务实例 8 并发用户（vLLM Blackwell 指南）；4×H100 27B 聚合 22K tok/s。

### 6.5 实际使用画像·最终方案（2026-09-16 定稿口径：白天 50 并发语音 + 夜间长文批处理，时间分离）

**画像**（用户 2026-09-16 确认）：262K/1M 长上下文**只用于知识库分析/总结**，属偶发批处理且**在下班后零并发时段跑**——硬件只需满足 max(白天负载, 夜间负载)，不是两者之和。

| 时段 | 负载 | 需求 |
|---|---|---|
| 白天 | 50 路并发语音（活动上下文 8-16K/路 + 共享前缀 1 份） | LLM KV ~50-100GB、聚合解码 2-3K tok/s；ASR 50 路流式（1.7B RTF~0.3，单卡从容；0.6B 档官方 128 并发/TTFT 92ms 实证） |
| 夜间 | 262K/1M 知识分析批任务，零并发 | 262K 单任务 KV 16GB 随意放；**1M 单任务 FP8 KV 32GB+FP8 权重 27GB=59GB，单张 96GB 卡直接装**（1M prefill 单卡 ~10-15 分钟，8 小时夜窗串行 30-50 个/4 卡并行 100+） |

**结论**：时间分离使企业档配置坍缩到 **4 卡工作站级**即可覆盖 50 并发+夜间 1M（详见 §7.4 方案零）；高可用再翻节点。双 5090（64GB）扛 50 路不建议（KV 池仅 ~35GB、ASR 同卡竞争、夜间 1M 装不下），定位 ≤15-20 路小团队。

**双 DGX Spark 判定（2026-09-16 三轮，按实际画像）**：整机=GB10（Grace 20 核 Arm + Blackwell 1000 TOPS FP4、128GB 统一 LPDDR5x @273GB/s、1-4TB NVMe、2×ConnectX-7、~$4-5k/台，官方双件套含 QSFP）。
- **白天语音**：TP2 集群 NVFP4 批处理聚合 ~0.8-1.5K tok/s → **每路 16-30 tok/s**——语音 TTS 消耗 ~4-5 tok/s 理论上够喂，但余量薄、TTFT 波动风险、ASR 50 路同机无实证（最坏要 1 台专跑 ASR，LLM 退回单机）。**50 路满配不推荐；≤20-25 路可作预算敏感选项（需实测）**。
- **夜间长文**：✅✅ 优秀——1M FP8 KV 32GB+权重在 128GB 统一内存轻松，FP4 算力 prefill 够用；双机 256GB。
- **定位**：**入门一体档**（~¥8-9 万）——白天 10-25 路 + 夜间 1M 全能，适合预算敏感的 10-20 人客服团队；不与主力档竞争。买它当「夜间专用分析机」不成立（主力机夜间本闲，时间分离下重复投资）。
- 完整档位五要素表见 §7.5。
